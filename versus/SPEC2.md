# versus — технический контракт этапа 2

Продолжение [SPEC.md](./SPEC.md) ( этап 1, живые краш-тесты ). Контекст — [../VERSUS_PLAN.md](../VERSUS_PLAN.md).

Этап 2 добавляет то, ради чего раздел вообще похож на 1vs1.site: **выбор двух фреймворков и страница их сравнения** по статическим категориям. Краш-тесты становятся первой категорией на этой странице.

## Владение модулями

Чтобы исполнители не затирали друг друга. Зона одна, владелец один; в чужую не писать даже мелочь — присылать владельцу.

| Путь | Владелец на этапе 2 |
|---|---|
| `versus/data/` | `versus-data` |
| `versus/versus.*` — главная раздела | `versus-picker` |
| `app/`, `top/` — роутинг, мета, навигация | `versus-picker` ( передано от `versus-page` ) |
| `versus/pair/` — страница пары | `versus-pair` |
| `content/sitemap.xml` и маршруты пререндера | `versus-page` |
| `versus/case/`, `lab/`, `assets/versus/` | Заморожены, этап 1 закрыт |

`app/` и `top/` на этапе 1 принадлежали `versus-page`, на этапе 2 переходят к `versus-picker`: там правится ровно то, что он и делает — `route_args()`, `meta()`, `body_content()`. Ветки `versus` в них уже написаны под этап 1, их надо **дополнить** под пару, а не переписать.

Главная раздела `$bog_smalljs_versus` тоже уже существует и наполнена — заголовок, интро, блок «How this is measured». Этап 2 **надстраивает** над ней селектор пары, популярные сравнения и топы, а четыре блока краш-тестов переносит на страницу пары. Писать её с нуля не надо.

## Что попадает в sitemap

Число пар растёт как C(n,2): 6 фреймворков — 15 пар, 12 — уже 66. Ограничивать надо не потолком, а правилом:

**Пара попадает в карту, только если у обеих сторон есть файл данных с непустыми метриками.** Правило самоограничивается, совпадает с железным правилом про «ни одного выдуманного числа» и отсекает страницы, где обе колонки в прочерках. Такие в индексе вредят: тонкая страница без содержания роняет оценку раздела целиком.

Карту генерировать скриптом в `content/`, а не руками — при трёх парах это ещё выполнимо, при пятнадцати уже нет.

## Грабли, на которых тут легко подорваться

**Нормализацию порядка `a`/`b` нельзя делать из `@$mol_mem`.** Это запись в `$mol_state_arg`, а сеттер чужой ячейки, вызванный из тела `@$mol_mem`, даёт бесконечную инвалидацию. В том числе нельзя из `meta()` и `route_args()` — они мемоизированы. Только из `@$mol_action` или обработчика события.

**`$mol_link` с `arg` работает как toggle:** клик по ссылке, ведущей на текущее состояние, сбрасывает параметр и роняет на главную. В навигации по парам это заметно.

## Железное правило этапа

**Ни одного выдуманного числа.** Каждое значение приходит из измерения или из внешнего источника и несёт с собой ссылку и дату. Если данных нет — метрика **отсутствует** в JSON, а страница показывает «no data». Прочерк честен, правдоподобная выдумка — нет.

Весь раздел строится на том, что читатель может проверить любую цифру. Одно непроверяемое число обнуляет доверие ко всем остальным.

Это касается и оценок вроде «читаемость» — их нет как чисел. Читаемость показывается кодом рядом, это этап 3.

## Роутинг

| URL | Что |
|---|---|
| `section=versus` | Главная раздела: выбор пары, популярные сравнения, топы |
| `section=versus/a=react/b=vue` | Страница сравнения пары |

Порядок в URL нормализуется по алфавиту идентификаторов: `a=react/b=vue`, но `a=mol/b=react`. Если пришло наоборот — редирект на нормализованный вид, чтобы у страницы был один канонический адрес и поисковик не видел дублей.

`meta()` для пары: `title` вида `React vs Vue — $mol`, `description` с перечислением категорий. Канонический URL — нормализованный.

## Данные

Файлы: `versus/data/<framework>.json`, по одному на фреймворк. Плюс `versus/data/registry.json` с описанием метрик.

### `<framework>.json`

```json
{
  "id": "react",
  "title": "React",
  "since": 2013,
  "runner": true,
  "metrics": {
    "loc_todomvc": {
      "value": 832,
      "source": "bog/todomvc-compare/README.md",
      "measured_at": "2026-08-13",
      "method": "https://github.com/b-on-g/smalljs/tree/master/versus"
    }
  }
}
```

- `runner: true` только у тех, для кого есть живой раннер ( сейчас react, vue, mol ). У остальных категория краш-тестов на странице пары показывает «no live tests for this framework», а не пустоту.
- Метрики, которых нет, **просто отсутствуют**. Никаких `null`, `0` и `"n/a"`.
- `source` — путь в репозитории либо URL. Обязателен.
- `measured_at` — дата в ISO. Обязательна.

### `registry.json`

Описывает, как метрика называется, в чём измеряется, куда лучше и как её объяснить человеку:

```json
{
  "loc_todomvc": {
    "category": "code",
    "title": "Lines of code",
    "unit": "",
    "better": "lower",
    "human": "Fewer lines to read when someone else picks the project up."
  }
}
```

`better` — `lower`, `higher` или `boolean`. Поле `human` обязательно: это тот самый слой, без которого цифры ничего не говорят.

## Категории и метрики

| Категория | id | Метрики |
|---|---|---|
| Крайние случаи | `edge` | Живые краш-тесты этапа 1 |
| Код | `code` | `loc_todomvc`, `files_todomvc`, `deps_direct`, `deps_transitive`, `node_modules_size` |
| Вес и загрузка | `weight` | `bundle_gzip`, `framework_gzip`, `app_gzip`, `tti_3g`, `lighthouse` |
| Скорость | `speed` | `create_1k`, `update_1k`, `swap_rows`, `remove_row`, `mem_ready`, `mem_1k`, `startup_tbt` |
| Из коробки | `builtin` | `router`, `i18n`, `themes`, `virtual`, `offline`, `ssr`, `tests_nodom`, `di`, `forms`, `typed_templates` |
| Экосистема и рынок | `market` | `stars`, `npm_downloads`, `so_questions`, `jobs`, `ui_kits`, `maintainers`, `release_rate` |
| Стоимость владения | `cost` | `cve_tree`, `breaking_3y` |

Источники: `code` и `weight` частично уже намерены в `bog/todomvc-compare/`; `speed` — JSON форка js-framework-benchmark; `market` — GitHub и npm API; `cost` — osv.dev.

## Страница пары

```
Заголовок: React vs Vue
Вердикт:   «React wins 3 of 7 categories, Vue 2, two tied»
           Общего балла НЕТ.

для каждой категории:
  Название + балл обеих сторон
  строки метрик:  значение A | бар | значение B | «A is 62% faster»
                  под строкой — фраза из `human`
                  сбоку — ссылка на источник и дата замера

Первой идёт категория «Edge cases» — живые краш-тесты.
Внизу: «How this is measured» + форма «предложить фреймворк».
```

Балл категории: доля метрик, где сторона лучше, из числа метрик, **известных обеим сторонам**. Метрика, которой нет у одного из двух, в счёт не идёт и рисуется прочерком у обоих. Иначе фреймворк с более полными данными выигрывал бы за счёт заполненности таблицы, а не за счёт качества.

Ничья по категории — нормальный исход, её надо показывать словом, а не прятать.

## Краш-тесты на странице пары

`$bog_smalljs_versus_case` уже параметризован: `frameworks()` — переопределяемый метод. Для страницы пары он возвращает два идентификатора вместо трёх, остальное работает без изменений.

Если у одного из пары `runner: false` — блок краш-тестов показывает одну колонку и поясняет, что для второго живых тестов пока нет. Не выдумывать поведение фреймворка, для которого не написан раннер.

## Главная раздела

Копируем 1vs1.site по структуре: два поля с «vs» между ними выше сгиба, ниже «Популярные сравнения» на 9 готовых пар, ниже топы по 6 карточек, ниже таблица рейтинга с пагинацией.

Рейтинг сортируется по числу выигранных категорий против всех остальных. Если данных мало — строка всё равно есть, с пометкой о неполноте.

## Ограничения

- Тексты английские, через `@ \Text`.
- `as any` в стилях запрещён, стили только через `.view.css.ts`.
- Не запускать `npx mam`, билд идёт в фоне; результат смотреть в `bog/smalljs/app/-/web.audit.js`.
- Числа не выдумывать. Повторено намеренно.
