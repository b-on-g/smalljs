# versus — технический контракт этапа 1

Общая спека для всех исполнителей раздела `versus`. Читать целиком перед работой.
Контекст и мотивация — `../VERSUS_PLAN.md`.

**Язык всех пользовательских строк — английский** ( у smalljs EN-first ). Локализация — отдельной задачей позже, поэтому все тексты в view.tree писать через `@ \Text`, чтобы они попали в `*.locale=*.json`.

## Что строим на этапе 1

Раздел «Compare» с живыми краш-тестами. Пользователь открывает страницу, жмёт «Run» и видит, как один и тот же сценарий отрабатывает в React, Vue и $mol в трёх iframe рядом. Таблиц с цифрами на этом этапе нет.

**Тон:** мы не пишем «React сломался». Мы пишем, что наблюдали: «Selected user 5, panel shows user 1». Вывод делает читатель.

## Раскладка модулей

| Путь | Идентификатор | Что это |
|---|---|---|
| `bog/smalljs/versus/` | `$bog_smalljs_versus` | Страница раздела: заголовок, интро, список кейсов |
| `bog/smalljs/versus/case/` | `$bog_smalljs_versus_case` | Движок одного краш-теста: три iframe, кнопка Run, вердикты |
| `bog/smalljs/lab/` | `$bog_smalljs_lab` | $mol-приложение со всеми сценариями, грузится в iframe |
| `bog/smalljs/assets/versus/react/runner.html` | — | Статическое React-приложение со всеми сценариями |
| `bog/smalljs/assets/versus/vue/runner.html` | — | Статическое Vue-приложение со всеми сценариями |
| `bog/smalljs/assets/versus/vendor/` | — | Вендоренные UMD-бандлы React и Vue |

Файлы внутри `assets/` называются `runner.html`, а **не** `index.html`: папку с `index.html` MAM считает собираемым модулем, а эти страницы — статика, которую надо просто скопировать на прод.

### Адреса iframe

| Фреймворк | Путь |
|---|---|
| React | `bog/smalljs/assets/versus/react/runner.html?case=<id>` |
| Vue | `bog/smalljs/assets/versus/vue/runner.html?case=<id>` |
| $mol | `bog/smalljs/lab/-/index.html?case=<id>` |

Пути одинаковы на дев-сервере и на проде — меняется только префикс: на деве ведущий `/`, на проде относительный от корня сайта. Никакой отдельной папки `assets/versus/mol/` нет.

**Почему $mol-раннер лежит не в `assets`, а в своей сборке.** Он настоящий MAM-модуль, его собирает CI ( `modules: 'app lab'` ) и отдельным шагом копирует в выхлоп по тому же пути, что и на деве. Поэтому проверенное локально — буквально то, что уезжает на прод.

**Почему раннер лежит в `lab/`, а не в `versus/runner/`.** Изначально он был `$bog_smalljs_versus_runner` — и MAM затаскивал в его граф родительский путь `bog/smalljs/versus/`, то есть саму страницу раздела. Пока страница была статичной, это было незаметно. Как только на ней появился селектор, бандл раннера вырос с 407 до 427 КБ, и каждая правка страницы пересобирала раннер: iframe успевал подхватить недописанный файл и падал с `Unexpected end of JSON input`.

Получалась ещё и кольцевая зависимость по смыслу: страница встраивает раннер, раннер бандлит страницу. Имя `lab` выведено из пространства имён `versus`, поэтому теперь тянется только пустой `bog/smalljs/`.

Общее правило: **приложение, которое встраивается в iframe, не должно жить под пространством имён страницы, которая его встраивает.**

**Почему не `include` / `require` в `app.meta.tree`.** Обе директивы означают одно: вкомпилировать модуль в бандл сайта ( различаются только приоритетом: `include` = −999, `require` = 0 ). Отдельную страницу они не публикуют. Если сложить раннер в бандл сайта, iframe потянет всю документацию целиком — около 2.4 МБ вместо 400 КБ, и страница сравнения начнёт свидетельствовать против самой себя.

**Почему не `deploy \/bog/smalljs/lab/-`.** `deploy` копирует то, что лежит в папке на момент сборки `app`, и ничего не знает о том, собран ли уже `lab`. Явный шаг копирования после сборки обоих модулей такого допущения не делает.

`bog/smalljs/assets` уже прописан в `app/app.meta.tree` через `deploy`, поэтому всё под ним попадает на прод как есть.

**React и Vue подключать только вендоренными UMD-файлами.** `require('react')` в MAM затащит весь пакет в основной бандл сайта.

## Протокол iframe ↔ страница

Все сообщения — `postMessage` с полем `ns: 'versus'`. Чужие сообщения игнорировать по этому полю.

Страница → iframe:

```js
{ ns: 'versus', type: 'run',   case: 'race' }
{ ns: 'versus', type: 'reset' }
{ ns: 'versus', type: 'theme', lights: 'light' | 'dark' }
```

iframe → страница:

```js
{ ns: 'versus', type: 'ready',  case: 'race' }
{ ns: 'versus', type: 'result', case: 'race',
  status: 'ok' | 'warn' | 'fail',
  observed: 'Selected user 5, panel shows user 1',
  metrics: [ { name: 'DOM nodes', value: 10042, unit: '' } ] }
{ ns: 'versus', type: 'error',  message: '...' }
{ ns: 'versus', type: 'invalid', case: 'race', reason: 'tab-hidden' }
```

Правила:

- iframe шлёт `ready` сразу после монтирования сценария, до нажатия Run.
- Тема идёт **сообщением, а не в query-параметре**: смена `src` перезагрузила бы раннер и стёрла результат уже сделанного прогона, а переключить тему читатель может и после Run. Страница шлёт `theme` каждому фрейму сразу после его `ready` — иначе фрейм, догрузившийся после переключения, остался бы в чужой теме, — и повторно при каждой смене. Раннер применяет её без перезагрузки.
- Палитра раннеров прописана в них литералами и одинакова во всех шести: токены сайта внутри iframe недоступны, а колонки читаются рядом, и разница в оттенке между ними была бы прочитана как разница между фреймворками. Тёмный набор: фон `#18181b`, поверхность `#27272a`, текст `#d4d4d8`, линии `#3f3f46`.
- Сценарий выбирается query-параметром: `runner.html?case=race`.
- Отправитель определяется сравнением `event.source` с `contentWindow` конкретного iframe. По `origin` не фильтруем — dev и прод на разных путях.
- Страница ставит таймаут 15 с на `result`; по истечении — статус `error`.
- `status`: `ok` — поведение корректное, `fail` — наблюдается артефакт, `warn` — корректно, но с оговоркой ( например, работает, но ценой ручного кода ).
- `observed` — одна короткая английская фраза в прошедшем времени, только факт. Без оценок и без названий фреймворков.

## Сценарии MVP

Все три реализации должны быть визуально и по шагам одинаковы. Стили внутри iframe — минимальные, системный шрифт, светлый фон, ширина 100%.

### `race` — Stale response overwrites fresh one

- Слева список из 5 пользователей ( `User 1` … `User 5` ), справа панель с именем и описанием выбранного.
- «Загрузка» — `setTimeout`, задержка `1000 - index * 200` мс: у `User 1` — 1000 мс, у `User 5` — 200 мс.
- Run: программно выбираем `User 1`, ждём 100 мс, выбираем `User 5`, ждём 1500 мс, читаем результат. Именно последовательность из двух ожиданий — чтение происходит примерно на 1600 мс от старта Run, а не на 1500.
- `ok`, если панель показывает `User 5`. `fail`, если `User 1`.
- Метрика: нет.
- **React / Vue пишем ровно так, как пишут по умолчанию** — `useEffect` с `setData` без флага отмены; `watch` с `await` без проверки актуальности. Под iframe в UI подписываем, что это код без ручной отмены и что её можно дописать. Не делаем вид, что починить нельзя.
- $mol: значение вычисляется атомом от id, устаревший результат отбрасывается движком.

### `virtual` — 10 000 rows of irregular height

- Список из 10 000 элементов, высота каждого разная ( текст длиной `20 + (i * 37) % 400` символов ).
- **Страница монтируется с пустым списком.** Данные заливаются внутри Run — так метрика привязана к действию пользователя, честно перемеряется при повторном запуске, и человек своими глазами видит, что происходит в момент нажатия. Побочная выгода: Run инициирует человек, значит вкладка в этот момент заведомо видима и `requestAnimationFrame` работает.
- **До Run вместо пустой рамки — одинаковая во всех трёх раннерах строка-заглушка** `Press Run to load 10,000 rows`. Требование визуальной одинаковости колонок сохраняется, и заодно читателю заранее понятно, что произойдёт.
- **Строка списка — ровно один элемент**, текст внутри без вложенных тегов. Иначе разница между колонками окажется про то, кто как свёрстал строку, а не про фреймворк.
- Run по шагам:
  1. `t0 = performance.now()`
  2. подать в компонент 10 000 строк
  3. дождаться двух подряд `requestAnimationFrame`
  4. прочитать `container.scrollHeight` — это форсирует расчёт раскладки
  5. `t1 = performance.now()`, `Render time = Math.round( t1 - t0 )`
  6. программный скролл контейнера до 50 % и обратно, 2 секунды
  7. замер `DOM nodes`
- Метрики в этом порядке: `DOM nodes` ( `container.querySelectorAll('*').length` ), затем `Render time` в мс.
- `ok`, если узлов меньше 500. `fail`, если больше 5000. Между — `warn`.
- `observed` вида `Rendered 10042 DOM nodes for 10000 rows`.

Про то, что `Render time` включает раскладку браузера, а не только работу фреймворка: это сознательно. Пользователь ждёт именно первый кадр, а решение держать в DOM 10 000 узлов принимает фреймворк — значит и цена раскладки относится к нему. Замер без форсированной раскладки даёт числа, отличающиеся на порядок, и занижает то, что человек реально ощущает.
- React / Vue — обычный `.map()` без сторонней виртуализации. В UI подписываем, что виртуализацию подключают отдельной библиотекой.

### `leak` — Subscriptions after 100 mount cycles

- Общий store с массивом подписчиков. Компонент подписывается при монтировании.
- Run: 100 циклов монтирования и размонтирования, затем замер `store.subscribers.length`.
- Метрики: `Live subscribers`, `Heap` в МБ, если доступен `performance.memory`.
- `ok`, если подписчиков 0. `fail`, если больше 0.
- React / Vue — вариант без `return () => unsubscribe()`. В UI подписываем, что отписка пишется руками и её забывают.

### `crash` — One broken item takes down the tree

- Список из 20 карточек. У карточки №7 в данных `null` вместо объекта, обращение к полю кидает исключение при рендере.
- Run: подменяем данные так, что карточка №7 становится битой, перерисовываем.
- Метрики: `Surviving cards` — сколько карточек осталось в DOM.
- `ok` — выжило 19 **и** на месте №7 видна заглушка с ошибкой. `fail` — выжило 0. Всё остальное — `warn`, в том числе «выжило 19, но на месте №7 пусто и никакого следа ошибки в интерфейсе».
- Промежуточный исход не гипотетический: прод-сборка Vue перехватывает исключение внутри самого сломавшегося компонента и подставляет вместо него комментарий-ноду. Дерево цело, 19 карточек на месте, седьмая исчезает бесследно, `TypeError` уходит только в консоль. Это `warn`, и `observed` должен назвать вещи своими именами: `19 of 20 cards survived, card 7 disappeared without a placeholder`.
- Из этого следует требование к подписям в UI: под Vue **нельзя** писать, что дерево умирает — оно не умирает. У Vue отсутствует видимый след ошибки, а не изоляция. Разные исходы у трёх фреймворков здесь и есть полезный результат кейса.
- React / Vue — без `ErrorBoundary` / `errorCaptured`, как в дефолтном шаблоне. В UI подписываем, что перехват ошибок добавляется вручную и оборачивать надо каждую границу.

## Видимость вкладки

**В скрытой вкладке замеры недействительны, и это надо обрабатывать явно, а не надеяться.** Обнаружено при прогоне Vue-раннера, воспроизводится во всех браузерах на Chromium.

Что ломается:

- В фоновой вкладке Chrome поднимает минимальный интервал `setTimeout` примерно до 1000 мс. В `race` задержки 200 мс и 1000 мс схлопываются к одному значению, порядок ответов становится случайным, и артефакт, ради которого сценарий существует, пропадает. Четыре прогона подряд дали `fail`, `ok`, `ok`, `ok`.
- В фоновой вкладке `requestAnimationFrame` не срабатывает ни разу. Любой замер, который его ждёт, не завершается.

Почему это критично не только для разработки: читатель может нажать Run и переключиться на другую вкладку. Вернувшись, он увидит зелёную галочку у одного фреймворка и красный крест у другого — при том, что причина в планировщике браузера, а не в коде. Один такой скриншот в комментариях обнуляет доверие ко всему разделу.

Правила:

1. **Раннер обязан следить за видимостью на протяжении всего прогона.** Если вкладка была скрыта в любой момент между стартом Run и готовностью результата — слать `{ ns: 'versus', type: 'invalid', case, reason: 'tab-hidden' }` вместо `result`. Полурезультат не отправлять.

   **Проверять и состояние на старте прогона, и событие `visibilitychange`.** Это главное. `visibilitychange` срабатывает только на ПЕРЕХОД: если вкладка уже скрыта в момент нажатия Run, событие не придёт никогда, и проверка, подписанная только на него, промолчит. Одного лишь чтения состояния на старте тоже мало — вкладку могут увести уже во время прогона.

   Читать состояние через `document.visibilityState !== 'visible'`. Это тождественно `document.hidden` по спецификации; выбрано как единая форма для всех трёх раннеров, чтобы колонки нельзя было развести случайной разницей в проверке.

   Проверять подменой `document.hidden` или `visibilityState` вручную **нельзя** — такой тест подтверждает, что ветка кода работает, но ничего не говорит о том, вызывает ли её браузер. Уводить вкладку в фон по-настоящему.
2. **Страница не начинает прогон при `document.hidden === true`.** Кнопка Run в этот момент неактивна.
3. **По `invalid` страница показывает нейтральное состояние** — «замер прерван, вкладка уходила в фон» и предложение запустить снова. Это не ошибка и не вердикт, вердикт прошлого прогона при этом сбрасывается, а не остаётся висеть.
4. Метрику, которую не удалось честно померить, **не отправлять вовсе** — по тому же правилу, что и `Heap`. Прочерк лучше числа, которое померило ожидание вместо работы.

### `invalid` — одно состояние, несколько причин

Скрытая вкладка не единственный способ получить недостоверный замер. Все такие случаи идут одним типом `invalid` с разным полем `reason`; страница показывает их одинаково нейтрально, подставляя пояснение по причине. Заводить под них `error` нельзя: `error` означает, что раннер сломался, а здесь он цел и честно сообщает, что мерять было нечем.

| `reason` | Когда |
|---|---|
| `tab-hidden` | Вкладка уходила в фон во время прогона |
| `timers-throttled` | Вкладка видима, но прогон занял заметно дольше ожидаемого — таймеры зажаты нагрузкой машины. Для `race` порог 2200 мс при ожидаемых ~1600 |
| `frame-offscreen` | iframe уехал из вьюпорта во время прогона, браузер перестал давать ему кадры |

`frame-offscreen` ловится `IntersectionObserver` внутри раннера — наблюдать `document.documentElement` с `root: null`.

**Проверено экспериментально, потому что по букве спецификации работать не должно:** при `root: null` подразумеваемый корень — вьюпорт собственного документа, а раннер заполняет свой iframe целиком, то есть всегда обязан считаться видимым. На практике браузер клипает область пересечения по всей цепочке фреймов, поэтому наблюдатель внутри iframe видит вьюпорт **родительской** страницы. Никакой отдельной связи с родителем городить не нужно. Сценарий бытовой и частый: читатель жмёт Run и сразу листает вниз к следующему кейсу. Без этой проверки замер на двух `requestAnimationFrame` не завершится, кейс упрётся в пятнадцатисекундный таймаут страницы и покажет отказ — то есть страница обвинит фреймворк в том, что на самом деле сделал скролл читателя.

**Все три раннера обязаны реализовать все три причины одинаково.** Если офскрин ловит только один из них, колонки разъедутся: один покажет «замер не засчитан», а два других — вердикты, померенные в тех же негодных условиях.

## Уточнения к сценариям

Дописано после вопросов исполнителей. Обязательно к соблюдению всеми тремя раннерами — расхождение здесь делает сравнение недействительным.

**Промежуточные значения — всегда `warn`.** Пороги в сценариях задают только `ok` и `fail`. Всё, что между ними, — `warn`. Пример для `virtual`: меньше 500 узлов — `ok`, больше 5000 — `fail`, от 500 до 5000 включительно — `warn`. Придумывать свои границы нельзя.

**Счёт DOM-узлов.** Считаем внутри собственного контейнера сценария — того элемента, который скроллится и содержит строки, — а не по всему документу: `container.querySelectorAll('*').length`. Сам контейнер в счёт не входит. Одинаково во всех трёх раннерах, иначе цифры несопоставимы.

**`virtual` → метрика `Render time`.** Точные шаги — в описании сценария выше. Кратко: список монтируется пустым, строки заливаются внутри Run, замер от `performance.now()` перед подачей до чтения `container.scrollHeight` после двух подряд `requestAnimationFrame`. Округлять до целых миллисекунд.

**`leak` → метрика `Heap`.** Если `performance.memory` недоступен ( не-Chromium браузеры ), метрику **не отправлять вовсе** — не слать `null`, не слать `0`. Страница показывает прочерк для отсутствующих метрик. Статус кейса от наличия heap не зависит, он считается только по числу живых подписчиков.

**`crash` → пауза после подмены данных** — 200 мс, затем замер. Одинаково везде.

**Исключение внутри сценария — это результат, а не сбой.** Если фреймворк выбросил при рендере и снёс дерево, сценарий всё равно обязан посчитать метрики и отправить `result` с честным статусом. Тип `error` шлём только если сценарий не смог отработать вообще ( не смонтировался, упал сам раннер ) — то есть когда мерять нечего.

**Порядок метрик в массиве `metrics` фиксирован** и одинаков во всех раннерах: сначала метрика, по которой считается статус, затем вспомогательные. Страница выводит их в том порядке, в каком получила.

## Интеграция в приложение

В `app/app.view.ts`:

- `section()` — новое значение `versus`
- `route_args()` — `case 'versus': return [ [ 'section', 'versus' ] ]`
- `meta()` — своя ветка: `title` = `Compare — $mol`, `description` про интерактивное сравнение поведения фреймворков
- `body_content()` — `case 'versus': return [ this.Versus() ]`

В `app/app.view.tree` — `Versus $bog_smalljs_versus` на верхнем уровне, рядом с `Docs`, `Playground`, `Course`.

В `top/top.view.tree` — пункт `Nav_versus $mol_link` с `title @ \Compare` и `arg * section \versus`, `page \`, плюс такой же пункт в мобильном меню `Mobile_menu`. Ставить после `Nav_playground`.
