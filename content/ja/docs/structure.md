# プロジェクト構成

$mol のプロジェクトには入れ子になった 4 つの階層があります。クローンしてきた**ワークスペース**、その中の**パッケージ**、その中の**モジュール**、そしてモジュールの中の**ファイル**です。それぞれの階層は別々の問いに答えており、ビルドがすることの大半は、どれがどれなのかを知っていれば自然と分かります。

```
mam/                            ワークスペース — MAM のチェックアウト
├── .meta.tree                  レジストリ: どのパッケージがどのリポジトリ由来か
├── package.json
├── mol/                        パッケージ — フレームワーク本体、独立した git リポジトリ
│   └── button/                 モジュール — コンポーネント $mol_button
│       ├── button.view.tree
│       ├── button.view.ts
│       ├── major/              サブモジュール — $mol_button_major
│       └── minor/              サブモジュール — $mol_button_minor
└── my/                         パッケージ — あなたのもの
    ├── .gitattributes          `* -text` — ビルド済みバイナリを壊さない
    └── hello/                  モジュール — コンポーネント $my_hello
        ├── index.html          エントリポイント（アプリモジュールのみ）
        ├── hello.view.tree     レイアウト
        ├── hello.view.ts       振る舞い
        ├── hello.view.css.ts   スタイル、TypeScript で
        ├── hello.locale=ru.json
        ├── hello.meta.tree     ビルドとデプロイのディレクティブ
        ├── form/               サブモジュール — $my_hello_form
        ├── -view.tree/         hello.view.tree から生成
        └── -/                  ビルド出力
```

## ワークスペース

MAM は一度クローンして、その中で作業します。依存がコピーされてくるフォルダではありません。どのパッケージもそこに独立した git のチェックアウトとして、履歴つきで置かれているので、フレームワークのソースを読み、そこに `debugger` を差し込み、同じ作業コピーからプルリクエストを出せます。

ルートの `.meta.tree` が、それを成り立たせているレジストリです。

```tree
pack mol git \https://github.com/hyoo-ru/mam_mol.git
pack hyoo git \https://github.com/hyoo-ru/mam_hyoo.git
pack lib git \https://github.com/hyoo-ru/mam_lib.git
```

ビルドが `$mol_view` に出会ったとき `mol/` フォルダがまだ無ければ、ここで名前を引いてリポジトリをクローンします。何もベンダリングされず、何も平坦化されません。

## パッケージ

トップレベルのフォルダがパッケージであり、パッケージは git リポジトリです。自分のパッケージは、単に自分で名前を付けたフォルダにすぎません。ローカルにあるうちは登録は要らず、名前で取得したくなった日に `pack` の行が要ります。

パッケージは入れ子になります。パッケージは自分の中のフォルダのために独自の `pack` 宣言を持てて、MAM はそれをそのパッケージを収めることになるフォルダの `meta.tree` から読みます。このサイトは `bog/smalljs/` にあり、それ自体が 1 つのリポジトリで、`bog/bog.meta.tree` に載っています。そしてその `bog/bog.meta.tree` は、ルートの `.meta.tree` に載っている `bog/` のチェックアウトの中にあります。

### どのパッケージにも要るファイル

デプロイされるパッケージには、1 行だけの `.gitattributes` が要ります。

```
* -text
```

これは git の改行コード正規化を切ります。これが効いてくるのは、デプロイがビルド出力をブランチにコミットすることであり、その出力がテキストだけではないからです。このサイトは 57 個のバイナリファイル、つまり自前でホストしているフォントと、ページごとのプレビュー画像を積んでいます。入口で正規化されると、読者のもとには壊れた画像とフォントとして届き、それでいてビルド自体はグリーンのままです。MAM のチェックアウトもルートに同じファイルを持っていて、そこではフォント形式が追加で `binary` と印されています。

スキャフォルダはこれを書いてくれます。自分で始めたリポジトリには手で足してください。

## モジュール

モジュールはフォルダであり、フォルダはコンポーネントです。import 文もモジュールマップもありません。クラス名*そのもの*がアドレスで、その中のアンダースコアはそれぞれフォルダの区切りです。

```
$my_hello          →  my/hello/
$my_hello_form     →  my/hello/form/
$mol_button_major  →  mol/button/major/
$mol_after_frame   →  mol/after/frame/
```

解決の規則はこれで全部です。ビルダーはソースのテキストを走査して `$name` トークンを拾い、それぞれを `_` で分割し、フォルダをたどります。依存を宣言するものは何もありません。名前を使うことが宣言です。

実務上の帰結はこうです。**モジュールのフォルダ名にアンダースコアが入ることはありません。** `my/hello_form/` というフォルダは `my/hello/form/` として探され、決して見つかりません。症状は、エディタではコンパイルが通るのにバンドルに現れないクラスです。

サブモジュールを持つモジュールも、2 つの形のどちらかで、それ自身がコンポーネントでいられます。`$mol_button` は `major/` と `minor/` の隣、`mol/button/` に直接住んでいます。`$mol_view` は 1 階層深い `mol/view/view/` に住んでいます。`mol/view/` には `component/`、`selection/`、`tree2/` も入っているからです。MAM は先に二重のパスを試し、短いほうへ落ちるので、どちらの配置も解決されます。

## モジュールの中のファイル

どのファイルも任意です。モジュールとは、そこに入っているファイルの集まりにすぎません。

| ファイル | 用途 |
|------|---------|
| `hello.view.tree` | 宣言的なレイアウト |
| `hello.view.ts` | 振る舞い。生成された基底クラスを継承するクラス |
| `hello.view.css.ts` | 型付きのスタイル。末尾の `.ts` に注意してください。スタイルシートではなく、`$mol_style_define` を呼ぶ TypeScript です |
| `hello.ts` | ビューをまったく持たないモジュール — モデル、ユーティリティ、純粋なロジック |
| `hello.test.ts` | テスト。ビルダーが実行します |
| `hello.locale=ru.json` | 翻訳。`.locale=<lang>.json` で終わるファイルはすべて拾われます |
| `hello.meta.tree` | ビルドとデプロイのディレクティブ |
| `index.html` | エントリポイント。必要なのはアプリモジュールだけです |

拡張子の前に置く接尾辞は、ファイルを 1 つの環境に限定します。

- `frame.web.ts` — ブラウザバンドルだけ。`mol/after/frame/frame.web.ts` のように
- `build.node.ts` — Node バンドルだけ。MAM のビルダー自身のように
- `hello.test.ts` — テストバンドルだけ

ビルダーはアプリごとに `web` バンドルと `node` バンドルを作り、もう一方に印の付いたファイルを落とすので、プラットフォーム固有のコードが実行時に自分を守る必要はありません。

生の `.css` ファイルもモジュールの隣に置けます。型付きスタイルでは表せない少数のもの、たとえば `@keyframes` や `content:` のために、フレームワーク自身がそうしています。それ以外はすべて `.view.css.ts` に属し、そこではプロパティ名が検査されます。

## 生成されたフォルダはハイフンで始まる

MAM が名前をソースとして扱うのは、それが英数字で始まるときだけです。それ以外はビルドから見えません。生成されたフォルダに必ず `-` が付くのはそのためです。出力は入力のすぐ隣に置けて、しかも入力として読み戻されません。ワークスペースの `.gitignore` が `-*` を無視するのも同じ理由です。

**`-view.tree/`** は `.view.tree` ファイルの隣に現れ、ツリーがコンパイルされた結果を持ちます。

```
my/hello/-view.tree/
├── hello.view.tree.js            生成された基底クラス
├── hello.view.tree.d.ts          その型付きインタフェース
└── hello.view.tree.locale=en.json  抽出された @ 文字列
```

あなたの `hello.view.ts` は、その中のクラスを継承します。2 つのファイルの関係はそれだけです。[TypeScript から view.tree へ](#!section=docs/page=from-ts-to-view-tree) が、生成されたコードを 1 行ずつたどります。

**`-css/`** は生の `.css` ファイルの隣に現れ、そのスタイルシートを `$mol_style_attach` の呼び出しで包んだ、生成済みの `.ts` を持ちます。おかげでスタイルシートは `<link>` を必要とせず、バンドルと一緒に運ばれます。

**`-/`** は、あなたがビルドしたモジュールのビルド出力です。アプリなら `web.js`、`web.css`、`web.audit.js`、`web.d.ts`、`web.deps.json`、言語ごとの `web.locale=<lang>.json`、それらの `node` 版、書き換えられた `index.html`、そして生成された `package.json` と `manifest.json` が入ります。デプロイするのはこのフォルダです。`app/-` を静的ホストに公開する、それがデプロイ手順のすべてです。

これらを手で編集することはありません。ソースが変わるたびにビルダーが書き直すので、そこへの編集は次の保存で消え、理由を告げるエラーも出ません。`.view.tree` や `.css`、あるいはソースのほうを変えて、ビルドし直してください。

## meta.tree が実際にしていること

`meta.tree` はパッケージマニフェストではなく、依存も列挙しません。依存はコードから来ます。そこでは `$mol_view` というトークンがすでに宣言そのものだからです。`meta.tree` が運ぶのは、コードが自力では言えない一握りの事柄です。このサイトの `app/app.meta.tree` は、これでファイル全体です。

```tree
include \/mol/offline/install
include \/bog/builderui/theme.css
deploy \/bog/smalljs/assets
```

- **`deploy \/path`** はファイルまたはフォルダを `-/` へコピーし、ワークスペースからの相対パスを保ちます。`\/bog/smalljs/assets` は `app/-/bog/smalljs/assets/` に着地します。デプロイが運ぶ必要はあるのに、どのコードもインポートしない静的ファイル、つまり画像、フォント、アイコンのためのものです。
- **`include \/path`** と **`require \/path`** は、誰も参照していないモジュールを強制的に取り込みます。たとえば `\/mol/offline/install` は、読み込み時に登録する service worker が存在意義のすべてです。両者の違いは順序だけで、`require` はそのモジュールを取り込んだコードより前に、`include` は後ろに置きます。
- **`pack <name> git \<url>`** は上で述べたレジストリの項目で、そのパッケージを収めることになるフォルダの meta ファイルから読まれます。

MAM はフォルダ内の `*.meta.tree` をすべて読むので、名前は慣習を超えた意味を持ちません。モジュールの隣なら `<module>.meta.tree`、ワークスペースのルートなら `.meta.tree` です。

実際には `deploy`、`include`、`require` はアプリモジュールのものです。ビルドされデプロイされるのがそれだからです。普通のコンポーネントは自分のコードからすべてを解決するので、meta ファイルはまったく要りません。ライブラリモジュールがそれを持つのは、本当に参照されない依存があるときだけです。`mol/assert/assert.meta.tree` は `include \/mol/dev/format` の 1 行きりで、それが典型的な大きさです。

ディレクティブについて詳しくは [モジュールのメタデータ](#!section=docs/page=meta) を参照してください。
