# وضعیت و واکنش‌گرایی

وضعیت در $mol مانند یک صفحه‌گسترده رفتار می‌کند: شما اعلام می‌کنید که یک مقدار چگونه محاسبه می‌شود و هرچه به آن وابسته است خودبه‌خود به‌روز می‌شود. نه استوری، نه dispatch، نه هوکِ افکت — گراف وابستگی‌ها ردیابی می‌کند که چه چیزی باید بازمحاسبه شود.

## ویژگی‌های واکنش‌گرا

متدی که با `@ $mol_mem` تزئین شده یک سلولِ واکنش‌گرای کش‌شده است. یک‌بار اجرا می‌شود، نتیجه‌اش را به‌خاطر می‌سپارد و فقط زمانی بازمحاسبه می‌کند که چیزی که خوانده تغییر کرده باشد.

```typescript
namespace $.$$ {
	export class $my_counter extends $.$my_counter {
		@ $mol_mem count() { return 0 }

		@ $mol_mem doubled() {
			return this.count() * 2
		}
	}
}
```

`doubled` مقدار `count` را می‌خواند، پس به‌طور خودکار مشترکِ `count` می‌شود. `count` را تغییر دهید و هر نمایی که `doubled` را نشان می‌دهد تازه می‌شود — چیزی برای اشتراک دستی وجود ندارد.

## خواندن و نوشتن

یک ویژگی هم‌زمان getter و setter است: بدون آرگومان صدایش بزنید تا بخوانید، با یک آرگومان تا بنویسید.

```typescript
@ $mol_action
increment() {
	this.count( this.count() + 1 )
}
```

## کنش‌ها در برابر محاسبه‌ها

همین یک تمایز کدِ واکنش‌گرا را قابل‌پیش‌بینی نگه می‌دارد:

- `@ $mol_mem` یک **محاسبهٔ خالص** است — فقط سلول‌های دیگر را می‌خواند و یک مقدار برمی‌گرداند.
- `@ $mol_action` یک **افکت** است — نوشتن در وضعیت، فراخوانی‌های شبکه و تایمرها به اینجا تعلق دارند.

نوشتن در یک سلول از درونِ یک `@ $mol_mem` یک حلقهٔ بازخورد ایجاد می‌کند (نوشتن یک وابستگی را بی‌اعتبار می‌کند، که بازمحاسبه می‌شود، که دوباره می‌نویسد). $mol این را به‌عنوان *اشتراک حلقوی* گزارش می‌دهد. راه‌حل همیشه یکی است: اثرات جانبی را در کنش‌ها نگه دارید و محاسبه‌ها را خالص نگه دارید.

| در `@ $mol_mem` می‌توانید | اما نه |
|---|---|
| سلول‌های دیگر را بخوانید | در سلول‌های دیگر بنویسید |
| `new SomeClass()` | `fetch()`، `await` |
| یک مقدار برگردانید | `setTimeout`، نوشتن در DOM |

هندلرهای دکمه به‌صورت `@ $mol_mem` روی کلاس پایه تولید می‌شوند؛ آن‌ها را با `@ $mol_action` بازنویسی کنید تا بتوانند با ایمنی بنویسند:

```typescript
@ $mol_action
submit() {
	this.saved( true )
}
```

## وضعیت مشتق‌شده ترکیب می‌شود

چون وابستگی‌ها خودکار ردیابی می‌شوند، مقادیر مشتق‌شده بدون هیچ سیم‌کشی‌ای زنجیر می‌شوند. هر یک قبلی را می‌خواند؛ تغییری در ریشه دقیقاً تا هرجا که لازم است موج می‌زند:

```typescript
@ $mol_mem full_name() {
	return `${ this.first() } ${ this.last() }`.trim()
}

@ $mol_mem greeting() {
	return this.full_name() ? `Hello, ${ this.full_name() }!` : 'Hello!'
}
```

## وضعیت کلیددار

`@ $mol_mem_key` محاسبه‌ای است که با یک کلید پارامتری شده — یک سلولِ کش‌شده به‌ازای هر کلید. برای مقادیر هر ردیف ایده‌آل است:

```typescript
@ $mol_mem_key
task_done( id: string, next?: boolean ) {
	const task = this.task( id )
	if ( next !== undefined ) task.Done( null )!.val( next )
	return task.Done()?.val() ?? false
}
```

## ناهم‌زمان فقط یک مقدار است

از یک `@ $mol_mem` یک promise برگردانید و نما تا زمان حل‌شدن یک وضعیت بارگذاری نشان می‌دهد — بدون پرچمِ بارگذاریِ صریح:

```typescript
@ $mol_mem
async data() {
	const res = await fetch( '/api/data' )
	return await res.json()
}
```

[دریافت داده](#!section=docs/page=data) بر پایهٔ همین الگو ساخته شده است.

## وضعیت گذرا میان رویدادها

وضعیتی که در `view.tree` اعلام شده میان هندلرهای رویدادِ جداگانه بازنشانی می‌شود (توالی‌های کشیدن/جابه‌جایی/اشاره)، چون $mol هر هندلر را در فایبرِ خودش می‌پیچد. برای مقادیری که باید از یک رویداد تا رویداد بعدی زنده بمانند، به‌جای یک ویژگی واکنش‌گرا از یک فیلدِ سادهٔ TypeScript استفاده کنید:

```typescript
export class $my_canvas extends $.$my_canvas {
	// plain field — survives across events, not reactive
	drag_id = ''

	@ $mol_action pan_start() { this.drag_id = 'node_42' }
	@ $mol_action pan_move() { if ( this.drag_id ) { /* ... */ } }
}
```

وقتی نما باید به مقدار واکنش نشان دهد از یک سلول واکنش‌گرا استفاده کنید؛ برای وضعیت گذرایی که فقط هندلرها می‌خوانند از یک فیلد ساده استفاده کنید.

## بعدی

وضعیت واکنش‌گرا زمانی بیشترین کاربرد را دارد که آدرس‌پذیر باشد — آن را در [مسیریابی](#!section=docs/page=routing) به URL متصل کنید.
