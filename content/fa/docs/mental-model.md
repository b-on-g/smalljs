# مدل ذهنی

اگر از React یا Vue می‌آیید، روزهای نخست در $mol صرفِ گشتن به دنبال چیزهایی می‌شود که اصلاً وجود ندارند: `computed`، `watch`، `useEffect`، `onMounted`، یک `fetch` درونِ قلابِ چرخهٔ عمر. این‌ها جایی در API پنهان نشده‌اند؛ مدل جایی برایشان ندارد. این صفحه نسخهٔ پنج‌دقیقه‌ایِ همان مدل است. پیش از [نماها](#!section=docs/page=views) بخوانیدش و هر بار که نامی آشنا گم شد به آن برگردید.

## کشیدن، نه هل‌دادن

تا کسی چیزی را نخواند، محاسبه نمی‌شود. نما با خواندنِ ویژگی‌هایش رندر می‌شود؛ هر ویژگی هرچه لازم دارد می‌خواند؛ زنجیرهٔ وابستگی از همین خواندن‌ها خودش شکل می‌گیرد. نه اشتراکی برای اعلام‌کردن هست و نه `watch`ی برای ثبت‌کردن: خواندن، همان اشتراک است.

```tree
$my_profile $mol_view
	sub /
		<= Name $mol_view
			sub / <= name \
```

```typescript
namespace $.$$ {
	export class $my_profile extends $.$my_profile {
		@ $mol_mem
		user() {
			return this.$.$mol_fetch.json( 'https://api.example.com/me' ) as { name: string }
		}
		name() {
			return this.user().name
		}
	}
}
```

رندرشدنِ `Name` مقدارِ `name()` را می‌خواند، `name()` مقدارِ `user()` را می‌خواند و `user()` به شبکه می‌زند. هیچ‌کس به نما از درخواست نگفت و هیچ‌کس به درخواست از نما نگفت. وقتی `user()` تغییر کند، هرچه آن را خوانده بود بازمحاسبه می‌شود و هیچ‌چیز دیگری.

## بدون چرخهٔ عمر

نه `mounted`ی هست، نه `useEffect`ی، نه `created`ی. داده با خواندنِ یک ویژگی درخواست می‌شود و نما هنگام رندرشدن ویژگی‌هایش را می‌خواند. پس مثال بالا کاربر را همان لحظه‌ای بار می‌کند که `$my_profile` روی صفحه ظاهر می‌شود، نه زودتر. وقتی نما از صفحه بیرون برود دیگر کسی `user()` را نمی‌خواند و سلول همراهِ نما آزاد می‌شود.

جایگزینِ الگوی «واکشی هنگام mount» تماماً همین است: نما آنچه را لازم دارد می‌خواهد و فریم‌ورک تصمیم می‌گیرد کِی بپرسد. بارگذاری به رویدادِ صفحه بسته نیست؛ به دیده‌شدن بسته است.

## هر ویژگی یک سلول است

یک متد با یک آرگومانِ اختیاری هم‌زمان getter است و setter و مقدارِ محاسبه‌شده و وضعیت:

```typescript
@ $mol_mem
count( next?: number ) {
	return next ?? 0
}
```

بدون آرگومان صدایش بزنید می‌خواند، با آرگومان می‌نویسد. `@ $mol_mem` متد را به سلولی کش‌شده تبدیل می‌کند که هرگاه چیزی که خوانده تغییر کرده باشد بازمحاسبه می‌شود. مقدارِ محاسبه‌شده فقط یک متدِ `@ $mol_mem` است که متدهای دیگر را می‌خواند. به watcher نیازی نیست: اثرِ جانبی به یک رویداد تعلق دارد و هندلرِ رویداد متدی است که با `@ $mol_action` نشان‌دار شده.

```typescript
@ $mol_mem
doubled() {
	return this.count() * 2
}

@ $mol_action
increment() {
	this.count( this.count() + 1 )
}
```

[وضعیت و واکنش‌گرایی](#!section=docs/page=state) قاعده‌های آنچه را درونِ هرکدام از این دو مجاز است پوشش می‌دهد.

## کدِ هم‌زمانی که منتظر می‌ماند

`user()`ِ بالا هم‌زمان به نظر می‌رسد و چنان نوشته شده که انگار پاسخ از پیش آنجاست. کار می‌کند چون هر محاسبه‌ای درونِ یک فایبر اجرا می‌شود. `this.$.$mol_fetch.json()` آن فایبر را معلق می‌کند و فریم‌ورک پس از رسیدنِ پاسخ محاسبه را از نو راه می‌اندازد. تا آن لحظه نمایی که `user()` را خوانده وضعیتِ بارگذاری نشان می‌دهد؛ اگر درخواست شکست بخورد همان نما خطا را نشان می‌دهد. نه پرچمِ `isLoading` می‌نویسید و نه `try`/`catch`.

همین سازوکار به هر منبعِ ناهم‌زمانی خدمت می‌کند. [دریافت داده](#!section=docs/page=data) بارگذاریِ دوباره و رسیدگی به خطا را گام‌به‌گام نشان می‌دهد.

## همه‌چیز یک بازنویسی است

فایلِ `view.tree` فهرستی از اعلانِ متدهاست. هر خط زیرِ یک کامپوننت یکی از ویژگی‌های آن کامپوننت با مقدارِ پیش‌فرض است، و ویژگیِ هر کامپوننتِ تودرتو را می‌شود همان‌جا که استفاده شده با یک خط از نو تعریف کرد. placeholderِ یک ورودیِ متنی همان ویژگیِ `hint`ِ `$mol_string` است:

```tree
$my_search $mol_view
	sub /
		<= Query $mol_string
			hint \Search
			value? <=> query? \
```

نه فهرستی از propها برای گسترش‌دادن هست، نه wrapperی برای نوشتن، نه forkی برای نگه‌داشتن. اگر کامپوننتی ویژگی‌ای داشته باشد، می‌توانید از بیرون تنظیمش کنید.

## چطور منبع‌ها را بخوانیم

بخشِ قبل پرسشِ اصلی را پیش می‌کشد: از کجا می‌دانید نامِ آن ویژگی `hint` است؟ پاسخ این است که نگاه می‌کنید، و فریم‌ورک طوری ساخته شده که نگاه‌کردن ارزان باشد.

**منبعِ فریم‌ورک کنارِ منبعِ شماست.** در فضای کاریِ MAM، `mol/string/string.view.tree` یک پوشه با `my/hello/` فاصله دارد. نه در `node_modules` است و نه درونِ یک باندل؛ همان جور فایلی است که خودتان می‌نویسید.

**نامِ کلاس همان مسیر است.** `$mol_string` در `mol/string/` می‌نشیند و `$mol_button_major` در `mol/button/major/`. هر زیرخط یک جداکنندهٔ پوشه است، پس هر نامی در درختِ شما همیشه به پوشه‌ای برای بازکردن تبدیل می‌شود. پشتیبانیِ ویرایشگر در صفحهٔ [ابزارها](#!section=docs/page=tooling) همین نام‌ها را برایتان کامل می‌کند.

**فایلِ `.view.tree`ِ یک کامپوننت فهرستِ کاملِ ویژگی‌های آن است، همراه با پیش‌فرض‌ها.** شکلِ مقدار نوعش را می‌گوید: `\` آغازگرِ رشته است، `/` فهرست، `*` دیکشنری، عددِ خالی عدد است، `true` و `false` بولین‌اند، `null` یعنی غایب، و `<=` یک زیرنما یا ویژگی‌ای گرفته‌شده از مالک را معرفی می‌کند. این بخشی از `mol/string/string.view.tree` است که برای یک ورودی اهمیت دارد:

```tree
$mol_string $mol_view
	dom_name \input
	enabled true
	field *
		^
		disabled <= disabled false
		value <= value_changed? <=> value? \
		placeholder <= hint_visible <= hint \
	attr *
		^
		type <= type? \text
```

بلند بخوانیدش. `dom_name \input`: این کامپوننت یک المانِ `input` رندر می‌کند. `enabled true`: یک ویژگیِ بولین که به‌طور پیش‌فرض روشن است. `field *` دیکشنریِ فیلدهای المانِ DOM است؛ نام‌های سمتِ چپ به DOM تعلق دارند و نام‌های سمتِ راست به کامپوننت، و آنکه از همه راست‌تر است همانی است که شما تنظیمش می‌کنید. پس `placeholder`ِ DOM از `hint` می‌آید که پیش‌فرضش رشتهٔ خالی است؛ `value`ِ DOM همان ویژگیِ نوشتنیِ `value?` است، و ویژگیِ `type` همان `type?`ِ نوشتنی است که پیش‌فرضش `text` است. یک placeholder، یک ورودیِ غیرفعال و یک فیلدِ گذرواژه در درختِ شما می‌شوند `hint`، `enabled false` و `type \password`.

**واسطِ نوع‌دار از همان درخت تولید می‌شود.** فایلِ `mol/string/-view.tree/string.view.tree.d.ts` همان ویژگی‌ها را به‌صورت امضاهای TypeScript فهرست می‌کند، و [مرجعِ API](#!section=docs/page=api-mol-string) در همین سایت از همان فایل ساخته می‌شود. هر سه با هم می‌خوانند چون هر سه از یک منبع می‌آیند.

**بیشترِ کامپوننت‌ها یک پوشهٔ `demo/` و یک `readme.md` همراه دارند.** `mol/string/demo/demo.view.tree` ورودی را با یک hint، به‌صورت غیرفعال و با یک مقدارِ از پیش تنظیم‌شده نشان می‌دهد. وقتی کامپوننتی را در وضعیتی خاص لازم دارید، نزدیک‌ترین دموِ آن را پیدا کنید و خطش را کپی کنید.

روی‌هم‌رفته، یک placeholder حدود یک دقیقه وقت می‌برد:

```bash
ls mol | grep string
cat mol/string/string.view.tree
```

زیرِ `$mol_string` عبارتِ `hint \` را می‌بینید و زیرِ `$mol_string`ِ خودتان `hint \Search` می‌نویسید.

## نام‌ها

همه‌چیز `snake_case` است: نامِ ویژگی‌ها در `view.tree`، نامِ متدها در TypeScript، و ویژگی‌هایی که فریم‌ورک برای استایل‌دهی روی گره‌های DOM می‌گذارد. زیرنماها با حرفِ بزرگ شروع می‌شوند (`Query`) و مقدارها با حرفِ کوچک (`query`).

نامِ درون درخت و نامِ متد در کلاس باید حرف‌به‌حرف یکی باشند. `exchange_form` در درخت و `exchangeForm` در کلاس دو ویژگیِ بی‌ربط‌اند: آنکه در کلاس است هرگز خوانده نمی‌شود، آنکه در درخت است پیش‌فرضش را نگه می‌دارد، و هیچ خطایی هم به شما نمی‌گوید. وقتی یک بازنویسی انگار هیچ کاری نمی‌کند، اولین چیزی که باید بررسی کنید همین است. [رفع اشکال](#!section=docs/page=troubleshooting) این مورد و بقیهٔ موردهایی را فهرست می‌کند که صفحه غلط است و کامپایلر ساکت.

## بعدی

حالا که مدل سر جایش است، [نماها](#!section=docs/page=views) نشان می‌دهد کامپوننت‌ها چطور اعلام و ترکیب می‌شوند، و [از React، Vue و Svelte](#!section=docs/page=rosetta) نام‌هایی را که از پیش می‌شناسید به نام‌های اینجا نگاشت می‌کند.
