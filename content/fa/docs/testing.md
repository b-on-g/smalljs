# تست‌نویسی

نمای $mol تابعی از وضعیتِ خودش است، و همین تغییر می‌دهد که یک تست چه شکلی دارد. سناریوی کاربر به‌صورتِ فراخوانیِ متدهای خودِ نما نوشته می‌شود: پیش‌نویس را بگذارید، کنش را اجرا کنید، آنچه را کاربر می‌دید بخوانید.

```typescript
app.draft( 'Milk' )
app.add()
$mol_assert_equal( app.item_title( 0 ), 'Milk' )
```

نه سلکتوری، نه مرورگری، نه Playwright و Cypressی، نه انتظاری برای هیچ‌چیز. همان فایل این‌ها را هم به شما می‌دهد:

- **سرعت.** تست‌ها در Node در چند میلی‌ثانیه اجرا می‌شوند؛ هزارتاشان حدود یک دقیقه وقت می‌برد. `node my/hello/-/node.test.js` تست‌های یک ماژول را اجرا می‌کند.
- **بدونِ هیچ راه‌اندازی.** یک `hello.test.ts` کنارِ کامپوننت را سازنده برمی‌دارد و در `-/node.test.js` کامپایل می‌کند. یکپارچه‌سازیِ مداوم با `mam_build` اجرایش می‌کند و وقتی تستی بیفتد ساخت را می‌شکند.
- **جایگزینیِ سرویس‌ها از راهِ زمینه.** هر تست `$`ِ خودش را می‌گیرد، و هرچه کامپوننت از راهِ `this.$.X` به آن می‌رسد با انتسابِ یک بدلِ تستی به همان `$` عوض می‌شود. دلیلِ نوشتنِ `this.$.$mol_fetch` به‌جای `$mol_fetch` همین است: اولی جایگزین‌شدنی است، دومی نه.
- **زمانِ ماک‌شده.** تایمرهایی که از راهِ زمینه ساخته شوند خودبه‌خود تیک نمی‌زنند؛ `$mol_after_mock_warp()` هرچه در صف است را اجرا می‌کند.
- **یک DOMِ واقعی هر وقت لازمش داشتید.** باندلِ Node جی‌اس‌دام را همراه دارد، پس `dom_node()` و `querySelectorAll` در همان فایلِ تست کار می‌کنند.

## یک سناریو از راهِ متدهای نما

فهرستِ کارها را از [کتابِ آشپزی](#!section=docs/page=cookbook) بردارید: یک رشتهٔ `draft?`، یک فهرستِ `items`، یک کنشِ `add` و یک کنشِ `delete`. تستش در `my/todo/todo.test.ts` می‌نشیند:

```typescript
namespace $ {
	$mol_test({

		'add an item and delete it'( $ ) {
			const app = $my_todo.make({ $ })

			app.draft( 'Milk' )
			app.add()
			$mol_assert_equal( app.items().length, 1 )
			$mol_assert_equal( app.item_title( 0 ), 'Milk' )
			$mol_assert_equal( app.draft(), '' )

			app.delete( 0 )
			$mol_assert_like( app.item_rows(), [] )
		},

		'blank draft adds nothing'( $ ) {
			const app = $my_todo.make({ $ })

			app.draft( '   ' )
			app.add()
			$mol_assert_like( app.items(), [] )
		},

	})
}
```

چند نکته که ارزشِ توجه دارند:

- فایلِ تست از `namespace $` استفاده می‌کند، نه از `$.$$`. زمینهٔ `$` به‌عنوان آرگومان می‌آید، برای هر تست تازه، و کامپوننت با `Klass.make({ $ })` ساخته می‌شود تا سرویس‌هایش را از همان زمینه بخواند.
- کلیک همان فراخوانیِ هندلر است. `app.add()` کاری است که دکمه می‌کند؛ `app.Add().click( event )` وقتی بخواهید اتصال را هم پوشش دهید از همان مسیر می‌رود.
- آنچه کاربر می‌بیند را بررسی کنید: `items()`، `item_rows()`، `sub()`، `title()`ِ یک زیرنما. مدلی که از راهِ صفحه بررسی شود بازنویسی‌ای را هم که از کلاس بیرون افتاده می‌گیرد، کاری که تستِ صرفاً مدل نمی‌کند.
- `$mol_assert_equal` بر پایهٔ هویت مقایسه می‌کند، `$mol_assert_like` ساختار را مقایسه می‌کند، و `$mol_assert_fail( ()=> ..., 'message' )` انتظارِ پرتاب دارد.
- نامِ تست همان توضیح است. در بدنه کامنتی نیست.

## ماک‌کردنِ یک سرویس

هر تست زمینه‌ای تازه می‌گیرد که از زمینهٔ سراسری مشتق شده است. پیش از ساختنِ کامپوننت یک زیرکلاس را به سرویسی روی همان `$` نسبت دهید، و هر `this.$.X`ِ درونِ کامپوننت به همان جایگزین می‌رسد. این هم بدلِ fetch برای کامپوننتِ `$my_users` از [دریافت داده](#!section=docs/page=data):

```typescript
namespace $ {
	$mol_test({

		'user names come from the response'( $ ) {
			$.$mol_fetch = class extends $.$mol_fetch {
				static override json( input: RequestInfo ) {
					if( String( input ).endsWith( '/users' ) ) return [ { id: 1, name: 'Ada' } ]
					return $mol_fail( new Error( 'Unexpected request: ' + input ) )
				}
			}
			const app = $my_users.make({ $ })
			$mol_assert_like( app.user_names(), [ 'Ada' ] )
		},

	})
}
```

`users()` در کامپوننت `this.$.$mol_fetch.json( ... )` را صدا می‌زند، پس درخواست به ماک می‌رود و مقدار هم‌زمان در دسترس است، بدونِ هیچ انتظاری. اگر کامپوننت `$mol_fetch.json( ... )`ِ سراسری را صدا زده بود، ماک اصلاً پرسیده نمی‌شد. ماک‌های توکار از پیش `fetch` و `XMLHttpRequest`ِ سراسری را روی زمینه با پروکسی‌هایی که پرتاب می‌کنند جایگزین می‌کنند، پس درخواستی که از کنارِ زمینه در برود به‌جای دست‌زدن به شبکه با صدای بلند می‌افتد.

همین الگو `$mol_state_arg` را برای URL، `$mol_state_local` را برای ذخیره‌سازی، و هر چیزِ دیگری را که کامپوننتتان از `this.$` می‌گیرد پوشش می‌دهد.

`$mol_test_mocks` هم هست، فهرستی از توابع که پیش از هر تستِ باندل، از جمله تست‌های ماژول‌های دیگر، روی زمینه اجرا می‌شوند. جای قاعده‌هایی است که همه‌جا برقرارند، همان‌طور که خودِ فریم‌ورک ماک‌هایش را ثبت می‌کند: بدلی از ذخیره‌سازی که هرچه بگیرد نگه می‌دارد، بومی‌سازی‌ای که دیکشنریِ خالی برمی‌گرداند، و همان منعِ شبکهٔ بالا. دادهٔ نمونه برای یک کامپوننت جایش آنجا نیست.

## زمان

تست‌های خودِ فریم‌ورک برای `$mol_after_timeout` و `$mol_after_frame` و خویشاوندانشان ماک ثبت می‌کنند، و آن ماک‌ها در باندلِ شما هم هستند. تایمری که با `new this.$.$mol_after_timeout( ms, task )` ساخته شود به‌جای زمان‌بندی به صف می‌رود و `$mol_after_mock_warp()` صف را اجرا می‌کند. برای toastی که خودش را پنهان می‌کند:

```typescript
@ $mol_mem toast( next?: string ) { return next ?? '' }

@ $mol_action notify( text: string ) {
	this.toast( text )
	new this.$.$mol_after_timeout( 3000, ()=> this.toast( '' ) )
}
```

تست زمان را با دست جلو می‌برد:

```typescript
'toast hides after the timer'( $ ) {
	const app = $my_greeter.make({ $ })
	app.notify( 'Saved' )
	$mol_assert_equal( app.toast(), 'Saved' )
	$mol_after_mock_warp()
	$mol_assert_equal( app.toast(), '' )
},
```

`setTimeout`ِ خالی درونِ یک نما ماک نمی‌شود و از تست هم بیشتر عمر می‌کند؛ این یکی از دلیل‌های ساختنِ تایمرها از راهِ زمینه است.

## از راهِ DOM

در باندلِ Node، `$mol_dom_context` یک پنجرهٔ جی‌اس‌دام است، پس نما در المان‌های واقعی رندر می‌شود. وقتی بررسی دربارهٔ نشانه‌گذاری است و نه وضعیت، از آن استفاده کنید:

```typescript
'greets by name'( $ ) {
	const app = $my_greeter.make({ $ })
	app.name( 'Ada' )
	$.$mol_dom_context.document.body.appendChild( app.dom_node() )
	app.dom_tree()
	$mol_assert_equal( app.Hello().dom_node().textContent, 'Hello, Ada!' )
	app.destructor()
},
```

`dom_node()` المان را می‌سازد، `dom_tree()` زیردرخت را رندر می‌کند، و `destructor()` نما را آزاد می‌کند تا سلول‌هایش از تست بیشتر عمر نکنند. ویژگی‌ای که زیرنما از نامش می‌گیرد، اینجا `[my_greeter_hello]`، همان سلکتوری است که وقتی `querySelector` را بر صدازدنِ زیرنما ترجیح می‌دهید به کار می‌آید.

جی‌اس‌دام دو شیء سراسری را ندارد که فیلدهای ورودی و حرکت‌ها سراغشان می‌روند، `ShadowRoot` و `PointerEvent`. `$mol_string`ی که بدونِ آن‌ها رندر شود یک `ReferenceError` لاگ می‌کند و خالی می‌ماند، در حالی که بقیهٔ درخت رندر می‌شود. آن‌ها را از پنجرهٔ جی‌اس‌دام قرض بگیرید؛ این قاعده‌ای بدونِ داده و برای هر تستی است، پس در `$mol_test_mocks` می‌نشیند:

```typescript
$mol_test_mocks.push( $ => {
	const win = $.$mol_dom_context
	Object.assign( globalThis, {
		ShadowRoot: win.ShadowRoot,
		PointerEvent: win.PointerEvent ?? win.MouseEvent,
	} )
} )
```

## آنچه تستِ Node پوشش نمی‌دهد

هندسه و استایل. اینکه دو بلوک در یک خط می‌نشینند یا نه، اینکه پنلی از صفحه بیرون می‌زند یا نه، اینکه تمِ تیره خوب خوانده می‌شود یا نه: هیچ‌کدام در جی‌اس‌دام وجود ندارند. برای چیدمانی که دستش زده‌اید، فایلِ `-/test.html`ِ ماژول را در مرورگر باز کنید که برنامه را سوار می‌کند و همان تست‌ها را هم آنجا اجرا می‌کند، و نگاه کنید.

## نکته‌های عملی

- **سکوت یعنی شکست.** تستی که یک assert را رد کرده و تستی که آویزان مانده یک شکل دارند: نه خروجی‌ای و نه فرایندی که تمام شود. دنبالِ `All tests passed` در انتها بگردید؛ اگر نبود، اول آخرین assert را بررسی کنید. تستِ `async` به یک ثانیه محدود است.
- **یکی را عمداً بشکنید.** وقتی اجرایی هیچ چاپ نمی‌کند، یک assert را برعکس کنید و مطمئن شوید شکست دیده می‌شود. مجموعه‌تستی که نتواند بیفتد هیچ‌چیز را نمی‌سنجد.
- **رشته‌های بومی‌سازی‌شده را بررسی نکنید.** مقدارهایی که در درخت با `@` نشان‌دار شده‌اند از راهِ بومی‌سازی حل می‌شوند، که در هر زمینهٔ تازه دوباره گرم می‌شود. ساختار را بررسی کنید، نه متنِ یک برچسب را.
