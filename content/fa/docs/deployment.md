# استقرار

اپلیکیشنِ ساخته‌شدهٔ $mol یک پوشه از فایل‌های ایستاست. نه سروری هست که اجرا شود، نه پروسهٔ Nodeای که زنده نگه دارید، و نه آداپتوری که انتخاب کنید: هرچه بتواند یک پوشه را میزبانی کند، اپلیکیشن را هم میزبانی می‌کند.

## چیزی که منتشر می‌کنید

ساخت همه‌چیز را در پوشهٔ `-/` داخلِ ماژول می‌نویسد:

```
my/hello/-/
├── index.html                 برای مسیرِ انتشار بازنویسی شده
├── web.js                     کلِ اپلیکیشن، یک فایل
├── web.css
├── web.locale=en.json         یکی برای هر زبان
├── manifest.json
└── …                          هرچه دستورِ `deploy` به اینجا آورده
```

همان پوشه، خودِ سایت است. از هر میزبانِ ایستایی سرو کنید، اپلیکیشن کار می‌کند.

باقیِ چیزها در `my/hello/` سورس‌اند و `-/` تولیدشده است: `.gitignore`ِ فضای کاری الگوی `-*` را نادیده می‌گیرد، پس خروجیِ ساخت هرگز واردِ تاریخچهٔ خودِ پروژه نمی‌شود. به وب از شاخهٔ استقرار می‌رسد.

## روایتِ کوتاه

اسکافولدر ورک‌فلو را می‌نویسد، پس پروژهٔ تازه با همان push منتشر می‌شود:

```bash
npx create-view-tree-lsp my/hello
git push
```

`.github/workflows/deploy.yml` ماژول را می‌سازد و `my/hello/-/` را به شاخهٔ `gh-pages` می‌فرستد. به‌محضِ اینکه در **Settings → Pages → Source** گزینهٔ *Deploy from a branch* با `gh-pages` باشد، گیت‌هاب همان شاخه را سرو می‌کند — و این دقیقاً مقدارِ پیش‌فرضِ مخزنی است که چنین شاخه‌ای دارد. اگر نشانی ۴۰۴ می‌دهد، اولین چیزی که باید دید همین تنظیم است.

از آن پس سایت روی `https://<user>.github.io/<repo>/` زندگی می‌کند.

## ورک‌فلو واقعاً چه می‌کند

دو اکشن آن را می‌برند و هرکدام چند ورودی می‌گیرند:

```yaml
- uses: hyoo-ru/mam_build@master2
  with:
      package: "my/hello"     # پوشه‌ای که ساخته می‌شود، نسبت به فضای کاری
      modules: "app"          # کدام ماژول‌های داخلش

- uses: hyoo-ru/gh-deploy@v4.4.1
  if: github.ref == 'refs/heads/main'
  with:
      folder: "my/hello/app/-"
```

`mam_build` فضای کاریِ MAM را دورِ بستهٔ شما می‌گستراند، توکن‌های `$name` را از کدتان به مخزن‌هایی که آن‌ها را دارند می‌رساند و می‌سازد. نه به lockfile نیاز دارد و نه به گامِ `npm install`: فهرستِ وابستگی‌ها همان رجیستریِ `.meta.tree` است، همان‌طور که [ساختارِ پروژه](#!section=docs/page=structure) می‌گوید.

`gh-deploy` پوشهٔ ساخته‌شده را در `gh-pages` کامیت می‌کند. `target-folder` آن را به‌جای ریشه در زیرپوشه می‌گذارد — پیش‌نمایشِ شاخه این‌طور ساخته می‌شود:

```yaml
- name: Deploy feature branch
  if: startsWith(github.ref, 'refs/heads/feature/')
  uses: hyoo-ru/gh-deploy@v4.4.1
  with:
      folder: "my/hello/app/-"
      target-folder: ${{ github.ref_name }}
```

آنگاه هر شاخهٔ `feature/*` نشانیِ خودش را روی همان سایتِ Pages دارد، و تریگرِ `delete` با رفتنِ شاخه پوشه را برمی‌دارد.

## یک فایل که استقرار به آن نیاز دارد

بسته‌ای که منتشر می‌شود، کنارِ خودش به `.gitattributes` با یک خط نیاز دارد:

```
* -text
```

استقرار یعنی کامیت‌کردنِ خروجیِ ساخت در یک شاخه، و آن خروجی تنها متن نیست. فونت‌ها و تصویرهایی که در راهِ آن کامیت نرمال‌سازی شوند، شکسته به دستِ خواننده می‌رسند، در حالی که خودِ ساخت سبز می‌ماند. اسکافولدر این فایل را می‌نویسد؛ در مخزنی که خودتان ساخته‌اید، دستی اضافه‌اش کنید.

## فایل‌هایی که باید در ریشهٔ سایت باشند

`deploy \/path` در `meta.tree` فایل را به `-/` کپی می‌کند و **مسیرش نسبت به فضای کاری را نگه می‌دارد**. برای دارایی‌هایی که کد به آن‌ها ارجاع می‌دهد درست است و برای فایل‌هایی که میزبان در ریشه دنبالشان می‌گردد نادرست. `CNAME`، `robots.txt`، صفحهٔ تأییدِ مالکیت در سرچ‌کنسول: این‌ها را با یک گامِ ورک‌فلو، بعد از ساخت و پیش از گامِ استقرار، کپی کنید.

```yaml
- name: Copy root-level files
  run: cp my/hello/public/CNAME my/hello/app/-/CNAME
```

## لینک‌های عمیق روی میزبانِ ایستا

اپلیکیشنی با مسیریابیِ مبتنی بر path (یعنی `/section=docs/page=views` و نه `#!section=docs`) تنها یک چیز از میزبان می‌خواهد: هر مسیرِ ناشناخته زیرِ نقطهٔ نصب باید `index.html`ِ اپلیکیشن را برگرداند. وگرنه نخستین ورود از یک لینکِ عمیق ۴۰۴ است و فقط پیمایش از صفحهٔ اصلی کار می‌کند.

گیت‌هاب Pages قاعدهٔ بازنویسی ندارد، پس راه از `404.html`ِ خودش می‌گذرد: برای هر مسیرِ ناشناخته سرو می‌شود و چند خط داخلش نشانی را به `index.html` برمی‌گردانند تا روتر آن را به مسیرِ واقعی باز کند. مثلِ فایل‌های بالا، کنارِ خروجیِ ساخت کپی‌اش کنید.

میزبان‌های دیگر آن را در یک خط می‌گویند: `try_files $uri /index.html` در nginx، `try_files {path} /index.html` در Caddy، و قاعدهٔ `/* /index.html 200` در Netlify.

اپلیکیشنی روی روترِ hash (همان پیش‌فرض) به هیچ‌کدامِ این‌ها نیاز ندارد: هرچه پس از `#` بیاید هرگز به سرور نمی‌رسد.

## پیش از push بررسی کنید

ساخت در ماشینِ خودتان و در CI یکی است، پس ممیزیِ سبز روی سیستم یعنی استقرارِ سبز:

```bash
npx mam my/hello/app
cat my/hello/app/-/web.audit.js
```

`Audit passed` تمامِ گزارش است. برای دیدنِ چیزِ واقعی، پوشه را با هر سرورِ ایستایی سرو کنید:

```bash
npx serve my/hello/app/-
```

## فراتر از GitHub Pages

هیچ‌کدام از این‌ها مخصوصِ گیت‌هاب نیست. خروجی یک پوشه است و استقرار یک کپی. Netlify، Cloudflare Pages، S3 پشتِ CDN، nginx روی VPS، ایمیجِ داکری با همین پوشه داخلش — گامِ ساخت همان `npx mam my/hello/app` است و آنچه بالا می‌فرستید `my/hello/app/-`.

برای نصبی که آفلاین هم کار کند، [آفلاین](#!section=docs/page=offline) سرویس‌ورکری می‌افزاید که باندل را کش می‌کند، و همان پوشه به اپلیکیشنی نصب‌شدنی بدل می‌شود.
