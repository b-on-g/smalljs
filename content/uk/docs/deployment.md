# Деплой

Зібраний $mol-застосунок — це тека зі статикою. Нічого запускати на сервері, нічого тримати живим у Node, немає з чого вибирати адаптер: де хоститься тека, там працює і застосунок.

## Що саме ви викладаєте

Збірка складає все в теку `-/` всередині модуля:

```
my/hello/-/
├── index.html                 переписаний під адресу, за якою лежить сайт
├── web.js                     весь застосунок, один файл
├── web.css
├── web.locale=en.json         по одному на мову
├── manifest.json
└── …                          усе, що притягнула директива `deploy`
```

Ця тека і є сайт. Віддайте її будь-яким статичним хостингом — застосунок запрацює.

Усе інше в `my/hello/` — вихідники, а `-/` згенерована: кореневий `.gitignore` ігнорує `-*`, тож результат збірки не потрапляє в історію самого проєкту. У мережу він їде з гілки деплою.

## Коротко

Воркфлоу пише скафолдер, тому новий проєкт публікується по пушу:

```bash
npx create-view-tree-lsp my/hello
git push
```

`.github/workflows/deploy.yml` збирає модуль і пушить `my/hello/-/` у гілку `gh-pages`. GitHub віддає її, щойно в **Settings → Pages → Source** обрано *Deploy from a branch* і гілку `gh-pages` — і це значення за замовчуванням для репозиторію, у якому така гілка з'явилася. Якщо адреса віддає 404, перевіряти треба насамперед це налаштування.

Далі сайт живе за адресою `https://<user>.github.io/<repo>/`.

## Що робить воркфлоу

Усю роботу тягнуть два екшени, і в кожного пара параметрів:

```yaml
- uses: hyoo-ru/mam_build@master2
  with:
      package: "my/hello"     # яку теку збирати, шлях від кореня воркспейса
      modules: "app"          # які модулі всередині неї

- uses: hyoo-ru/gh-deploy@v4.4.1
  if: github.ref == 'refs/heads/main'
  with:
      folder: "my/hello/app/-"
```

`mam_build` розгортає навколо вашого пакета воркспейс MAM, перетворює токени `$name` з коду на репозиторії, де ці імена живуть, і збирає. Йому не потрібен ані лок-файл, ані крок `npm install`: список залежностей — це реєстр у `.meta.tree`, як описано в [Структурі проєкту](#!section=docs/page=structure).

`gh-deploy` комітить зібрану теку в `gh-pages`. Параметр `target-folder` кладе її не в корінь, а у вкладену теку — так і робиться превʼю гілки:

```yaml
- name: Deploy feature branch
  if: startsWith(github.ref, 'refs/heads/feature/')
  uses: hyoo-ru/gh-deploy@v4.4.1
  with:
      folder: "my/hello/app/-"
      target-folder: ${{ github.ref_name }}
```

У кожної гілки `feature/*` зʼявляється своя адреса на тому ж сайті, а тригер `delete` прибирає теку, коли гілку видалено.

## Один файл, без якого деплой ламається

Пакету, який викладається, потрібен поруч `.gitattributes` з єдиним рядком:

```
* -text
```

Деплой — це коміт результату збірки в гілку, а в результаті не лише текст. Шрифти й картинки, нормалізовані дорогою в цей коміт, приїжджають до читача побитими, а сама збірка при цьому лишається зеленою. Скафолдер цей файл пише сам; у репозиторії, заведеному руками, додайте його руками.

## Файли, яким місце в корені сайту

`deploy \/path` у `meta.tree` копіює файл у `-/`, **зберігаючи шлях відносно воркспейса**. Для ассетів, на які посилається код, це правильно, а для файлів, які хостинг шукає в корені, — ні. `CNAME`, `robots.txt`, сторінка підтвердження прав у пошуковику: їх копіюють кроком воркфлоу після збірки й до кроку деплою.

```yaml
- name: Copy root-level files
  run: cp my/hello/public/CNAME my/hello/app/-/CNAME
```

## Глибокі посилання на статиці

Застосунку зі шляховим роутингом (`/section=docs/page=views`, а не `#!section=docs`) від хостингу потрібне одне: будь-який невідомий шлях усередині монтування має віддавати `index.html` застосунку. Інакше перший захід за глибоким посиланням — це 404, і працюють лише переходи з головної.

У GitHub Pages немає правил переписування, тому дорога лежить через його `404.html`: він віддається на будь-який невідомий шлях, і кілька рядків усередині повертають адресу в `index.html`, а роутер розгортає її в справжній маршрут. Копіюється поруч із результатом збірки — тим самим кроком, що й файли вище.

Решта хостингів каже це одним рядком: `try_files $uri /index.html` у nginx, `try_files {path} /index.html` у Caddy, правило `/* /index.html 200` у Netlify.

Застосунку на хеш-роутері (він за замовчуванням) нічого з цього не треба: усе, що після `#`, до сервера не доїжджає.

## Перевірити до пушу

Збірка та сама локально і в CI, тож зелений аудит на машині означає зелений деплой:

```bash
npx mam my/hello/app
cat my/hello/app/-/web.audit.js
```

`Audit passed` — це весь звіт. Щоб подивитися на справжній результат, віддайте теку будь-яким статичним сервером:

```bash
npx serve my/hello/app/-
```

## Не лише GitHub Pages

Нічого з написаного вище не привʼязане до GitHub. На виході тека, деплой — це копіювання. Netlify, Cloudflare Pages, S3 за CDN, nginx на VPS, docker-образ із цією текою всередині: крок збірки той самий `npx mam my/hello/app`, а заливаєте ви `my/hello/app/-`.

Якщо потрібна робота без мережі, [Офлайн](#!section=docs/page=offline) додає service worker, який кешує бандл, — і та сама тека перетворюється на застосунок, який можна встановити.
