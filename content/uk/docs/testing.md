# Тестування

Подання в $mol — це функція від свого стану, і це змінює те, як виглядає тест. Користувацький сценарій пишеться викликами власних методів подання: задати чернетку, виконати дію, прочитати те, що побачив би користувач.

```typescript
app.draft( 'Milk' )
app.add()
$mol_assert_equal( app.item_title( 0 ), 'Milk' )
```

Ні селекторів, ні браузера, ні Playwright із Cypress, ні очікування чогось. Той самий файл дає вам ще й таке:

- **Швидкість.** Тести виконуються в Node за мілісекунди; тисяча штук вкладається приблизно у хвилину. `node my/hello/-/node.test.js` ганяє тести одного модуля.
- **Нульове налаштування.** Файл `hello.test.ts` поруч із компонентом підхоплює складальник і компілює в `-/node.test.js`. Неперервна інтеграція на `mam_build` ганяє його й валить збірку, коли тест падає.
- **Підміну сервісів через контекст.** Кожен тест дістає власний `$`, і все, до чого компонент дотягується через `this.$.X`, підміняється присвоєнням дублера в цей `$`. Саме тому треба писати `this.$.$mol_fetch`, а не `$mol_fetch`: перше замінне, друге — ні.
- **Змокований час.** Таймери, створені через контекст, самі не цокають; `$mol_after_mock_warp()` виконує все, що стоїть у черзі.
- **Справжній DOM, коли він потрібен.** У Node-бандлі їде jsdom, тож `dom_node()` і `querySelectorAll` працюють у тому самому тестовому файлі.

## Сценарій через методи подання

Візьмімо список справ зі [Збірника рецептів](#!section=docs/page=cookbook): рядок `draft?`, список `items`, дія `add` і дія `delete`. Його тест живе в `my/todo/todo.test.ts`:

```typescript
namespace $ {
	$mol_test({

		'add an item and delete it'( $ ) {
			const app = $my_todo.make({ $ })

			app.draft( 'Milk' )
			app.add()
			$mol_assert_equal( app.items().length, 1 )
			$mol_assert_equal( app.item_title( 0 ), 'Milk' )
			$mol_assert_equal( app.draft(), '' )

			app.delete( 0 )
			$mol_assert_like( app.item_rows(), [] )
		},

		'blank draft adds nothing'( $ ) {
			const app = $my_todo.make({ $ })

			app.draft( '   ' )
			app.add()
			$mol_assert_like( app.items(), [] )
		},

	})
}
```

На що варто звернути увагу:

- Тестовий файл використовує `namespace $`, а не `$.$$`. Контекст `$` приходить аргументом, свіжий на кожен тест, а компонент створюється через `Klass.make({ $ })`, щоб читати сервіси з цього контексту.
- Клік — це виклик обробника. `app.add()` — те, що робить кнопка; `app.Add().click( event )` іде тим самим шляхом, коли ви хочете захопити й прив'язку.
- Перевіряйте те, що бачить користувач: `items()`, `item_rows()`, `sub()`, `title()` підвиду. Модель, перевірена через екран, заодно ловить перевизначення, що випало з класу, чого тест самої лише моделі не помітить.
- `$mol_assert_equal` порівнює за ідентичністю, `$mol_assert_like` порівнює структуру, `$mol_assert_fail( ()=> ..., 'message' )` очікує винятку.
- Ім'я тесту і є описом. Коментарів у тілі немає.

## Мок сервісу

Кожен тест отримує свіжий контекст, похідний від глобального. Присвойте сервісу в цьому `$` нащадка до створення компонента — і кожне `this.$.X` усередині компонента розв'яжеться в підміну. Ось дублер fetch для компонента `$my_users` з [Отримання даних](#!section=docs/page=data):

```typescript
namespace $ {
	$mol_test({

		'user names come from the response'( $ ) {
			$.$mol_fetch = class extends $.$mol_fetch {
				static override json( input: RequestInfo ) {
					if( String( input ).endsWith( '/users' ) ) return [ { id: 1, name: 'Ada' } ]
					return $mol_fail( new Error( 'Unexpected request: ' + input ) )
				}
			}
			const app = $my_users.make({ $ })
			$mol_assert_like( app.user_names(), [ 'Ada' ] )
		},

	})
}
```

`users()` у компоненті викликає `this.$.$mol_fetch.json( ... )`, тож запит іде в мок, а значення доступне синхронно, без жодного очікування. Якби компонент викликав глобальний `$mol_fetch.json( ... )`, мока ніхто б не спитав. Вбудовані моки й так підміняють у контексті глобальні `fetch` і `XMLHttpRequest` проксі-об'єктами, що кидають виняток, тож запит, який прослизнув повз контекст, падає гучно, а не лізе в мережу.

Той самий прийом покриває `$mol_state_arg` для URL, `$mol_state_local` для сховища й усе інше, що компонент бере з `this.$`.

Є ще `$mol_test_mocks` — список функцій, які проганяються по контексту перед кожним тестом у бандлі, включно з тестами інших модулів. Це місце для правил, чинних усюди, — так фреймворк реєструє власні моки: дублер сховища, що запам'ятовує все віддане йому, локаль, яка повертає порожній словник, заборона мережі з абзацу вище. Фікстурам одного компонента там не місце.

## Час

Власні тести фреймворка реєструють моки для `$mol_after_timeout`, `$mol_after_frame` і їхньої рідні, і ці моки є й у вашому бандлі. Таймер, створений через `new this.$.$mol_after_timeout( ms, task )`, потрапляє в чергу замість планування, а `$mol_after_mock_warp()` цю чергу виконує. Нехай є тост, що ховається сам:

```typescript
@ $mol_mem toast( next?: string ) { return next ?? '' }

@ $mol_action notify( text: string ) {
	this.toast( text )
	new this.$.$mol_after_timeout( 3000, ()=> this.toast( '' ) )
}
```

тоді тест рухає час руками:

```typescript
'toast hides after the timer'( $ ) {
	const app = $my_greeter.make({ $ })
	app.notify( 'Saved' )
	$mol_assert_equal( app.toast(), 'Saved' )
	$mol_after_mock_warp()
	$mol_assert_equal( app.toast(), '' )
},
```

Голий `setTimeout` у поданні не мокається й переживає тест; це одна з причин створювати таймери через контекст.

## Через DOM

У Node-бандлі `$mol_dom_context` — це вікно jsdom, тож подання малюється у справжні елементи. Користуйтеся цим, коли перевірка про розмітку, а не про стан:

```typescript
'greets by name'( $ ) {
	const app = $my_greeter.make({ $ })
	app.name( 'Ada' )
	$.$mol_dom_context.document.body.appendChild( app.dom_node() )
	app.dom_tree()
	$mol_assert_equal( app.Hello().dom_node().textContent, 'Hello, Ada!' )
	app.destructor()
},
```

`dom_node()` створює елемент, `dom_tree()` малює піддерево, а `destructor()` звільняє подання, щоб його комірки не пережили тест. Атрибут, який підвид отримує від свого імені, тут `[my_greeter_hello]`, і є селектором, коли `querySelector` вам миліший за виклик підвиду.

У jsdom бракує двох глобальних об'єктів, за якими тягнуться поля вводу та жести, — `ShadowRoot` і `PointerEvent`. Намальований без них `$mol_string` пише в лог `ReferenceError` і лишається порожнім, поки решта дерева малюється. Позичте їх у вікна jsdom; це правило без жодних даних, спільне для кожного тесту, тож йому місце в `$mol_test_mocks`:

```typescript
$mol_test_mocks.push( $ => {
	const win = $.$mol_dom_context
	Object.assign( globalThis, {
		ShadowRoot: win.ShadowRoot,
		PointerEvent: win.PointerEvent ?? win.MouseEvent,
	} )
} )
```

## Чого Node-тест не покриває

Геометрію й оформлення. Чи лягають два блоки в ряд, чи вилазить панель за екран, чи читається темна тема — нічого цього в jsdom немає. Для верстки, якої ви торкалися, відкрийте `-/test.html` модуля в браузері — він монтує застосунок і ганяє там ті самі тести — і подивіться очима.

## Нотатки з практики

- **Тиша — це падіння.** Тест, що завалився на перевірці, і тест, що завис, виглядають однаково: виводу немає, процес живий. Шукайте `All tests passed` наприкінці; якщо цього рядка немає, починайте з останньої перевірки. Асинхронний тест обмежений однією секундою.
- **Зламайте один навмисно.** Коли прогін нічого не друкує, переверніть перевірку й переконайтеся, що падіння видно. Набір тестів, який не вміє падати, нічого не вимірює.
- **Не перевіряйте локалізовані рядки.** Значення, позначені в дереві через `@`, розв'язуються через локаль, а вона в кожному свіжому контексті прогрівається наново. Перевіряйте структуру, а не текст підпису.
