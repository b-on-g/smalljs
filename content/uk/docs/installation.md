# Встановлення

[Початок роботи](#!section=docs/page=getting-started) крок за кроком проведе вас через ваш перший застосунок. Ця сторінка — довідник: як влаштовано проєкт $mol і як працює збірка.

## Вимоги

- **Node.js 18+** та **git**. Більше нічого не встановлюється глобально.

## Робочий простір MAM

Застосунки $mol живуть усередині **MAM** — інструмента збірки та реєстру модулів. Ви клонуєте його один раз і розробляєте свої модулі всередині:

```bash
git clone https://github.com/hyoo-ru/mam.git ./mam
cd mam
npm install
npm start
```

`npm start` запускає стежачий сервер розробки на `http://localhost:9080/`. Він перезбирає під час збереження й автоматично розв'язує залежності — ви ніколи не супроводжуєте конфігурацію збирача.

## Як іменуються модулі

Кожне ім'я компонента відповідає шляху до теки, і **кожне підкреслення є роздільником тек**:

```
$my_app          →  my/app/
$my_app_header   →  my/app/header/
```

Імена тек модулів ніколи не містять підкреслення — для назв із кількох слів використовуйте вкладені теки. Якщо компонент, який ви використовуєте, ніколи не з'являється у збірці, майже завжди шлях до теки не збігається з іменем класу.

## Будова модуля

Компонент — це тека, яка містить до чотирьох файлів:

| Файл | Призначення |
|------|------|
| `name.view.tree` | Декларативна розмітка |
| `name.view.ts` | Поведінка (TypeScript) |
| `name.view.css.ts` | Типізовані стилі |
| `name.view.tree`, `index.html` | Точка входу для модуля-застосунку |

`index.html` застосунку монтує кореневий компонент:

```html
<body mol_view_root>
	<div mol_view_root="$my_app"></div>
	<script src="web.js"></script>
</body>
```

## Збірка для продакшену

Сервер розробки збирає на льоту, але ви можете зібрати будь-який модуль явно з кореня робочого простору:

```bash
npm run start my/app
```

Результат потрапляє в `my/app/-/` — разом із `web.js`, `web.css` та `web.audit.js`. **Завжди перевіряйте аудит:** чистий `web.audit.js` означає відсутність невикористаних залежностей і помилок типів.

## Додавання npm-пакетів

Пошліться на пакет через `require`, і MAM встановить його під час наступної збірки й покладе в бандл:

```typescript
const dayjs = require( 'dayjs' ) as typeof import( 'dayjs' )
```

### Завантаження пакета в рантаймі

Важкій бібліотеці, потрібній одному екрану, не обов'язково лежати у `web.js`. Покладіть її готовий браузерний файл поруч із бандлом і завантажуйте під час першого звернення.

Вкажіть файл у `meta.tree` модуля:

```tree
deploy \/node_modules/@turf/turf/turf.min.js
```

`deploy` встановить пакет, якщо його немає, і скопіює файл у `-/node_modules/@turf/turf/turf.min.js` — і на дев-сервері, і в продакшн-збірці. Завантажуйте його через `$mol_import.script`:

```typescript
namespace $ {
	export class $my_app_turf extends $mol_object {

		@ $mol_mem
		static api() {
			$mol_import.script( './node_modules/@turf/turf/turf.min.js' )
			return ( globalThis as any ).turf as typeof import(
				'@turf/turf'
			)
		}

	}
}
```

- Шлях відносний і розв'язується від сторінки в `-/`, тому той самий код працює на дев-сервері, у `test.html` і під час деплою в підпапку. Початковий `/` працює, лише поки застосунок лежить у корені домену.
- `$mol_import.script` призупиняє фібру до завантаження скрипта й кешує за URL: файл завантажується один раз, а все, що читає `$my_app_turf.api()` усередині `$mol_mem`, просто чекає на нього.
- Глобальне ім'я, тут `turf`, — те, яке призначає браузерна збірка бібліотеки. Яке саме, написано в її README.
- `typeof import( … )` дає повну типізацію. Тримайте ім'я пакета на окремому рядку: збирач вважає залежністю `require( '…' )` та `import( '…' )`, записані в один рядок, і все-таки покладе весь пакет у `web.js`.
