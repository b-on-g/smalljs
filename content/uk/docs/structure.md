# Структура проєкту

У $mol-проєкта чотири вкладені рівні: **воркспейс**, який ви склонували, **пакети** всередині нього, **модулі** всередині пакетів і **файли** всередині модуля. Розкладка відповідає на одне практичне питання — куди класти новий проєкт і кому належить його історія, — і майже все, що робить збірка, випливає з неї.

```structure
mam/                         воркспейс — склонований MAM
├── .meta.tree               реєстр: який пакет із якого репозиторію
├── mol/                     пакет — сам фреймворк, свій git-репозиторій
└── my/                      пакет — ваш, ваш git-репозиторій
    ├── .gitattributes       зберігає зібрані бінарники цілими
    ├── my.meta.tree         реєстр ваших проєктів
    └── hello/               проєкт — модуль і свій git-репозиторій
        ├── index.html       точка входу (лише в модулів-застосунків)
        ├── hello.view.tree
        └── form/            підмодуль — $my_hello_form
```

На цій сторінці біля кожного рядка листингу є знак питання з причиною, чому він тут; розділи нижче кажуть те саме докладно.

## Як завести проєкт

П'ять кроків. Повторюється лише перший, а останні три за вас може зробити скафолдер.

**1. Склонуйте воркспейс, один раз.** Усе, що ви напишете далі, живе всередині нього.

```bash
git clone https://github.com/hyoo-ru/mam.git
cd mam
```

**2. Заведіть свій пакет.** Одна коротка тека — ваше ім'я, ваша компанія, ваш нік — і власний git-репозиторій. Це контейнер для всіх проєктів, які ви почнете:

```bash
mkdir my
cd my
git init
```

Викладіть його туди, де тримаєте код, публічно чи приватно. Заразом покладіть поруч `.gitattributes` з єдиним рядком `* -text`; навіщо — у розділі про пакети нижче.

**3. Додайте реєстр.** `my/my.meta.tree` — список проєктів усередині вашого пакета. Він починається порожнім і отримує по рядку на проєкт:

```tree
pack hello git \https://github.com/you/hello.git
```

MAM читає його так само, як кореневий `.meta.tree` рівнем вище, тож колега, який склонував `my/`, отримає й проєкти.

**4. Створіть проєкт із власним репозиторієм.** Тека і є компонент — `my/hello/` це `$my_hello`, — а історія належить йому, а не вашому пакету й не $mol:

```bash
mkdir hello
cd hello
git init
```

У цьому розділенні й сенс розкладки: коміт у `my/hello/` іде в репозиторій `hello`, ніколи не в `my` і не в `mol`.

**5. Пропишіть його.** Додайте рядок `pack` із кроку 3 у `my/my.meta.tree` — і свіжий чекаут вашого пакета підтягне проєкт за іменем.

[Скафолдер](#!section=docs/page=tooling) напише робочий модуль за вас будь-коли після другого кроку:

```bash
npx create-view-tree-lsp my/hello
```

## Робочий простір

MAM клонують один раз і працюють усередині нього. Це не тека, куди копіюються залежності: кожен пакет лежить там власним git-чекаутом, з історією, тож ви можете читати вихідники фреймворка, поставити в них `debugger` і відкрити pull request із тієї самої робочої копії.

Кореневий `.meta.tree` — реєстр, який це забезпечує:

```tree
pack mol git \https://github.com/hyoo-ru/mam_mol.git
pack hyoo git \https://github.com/hyoo-ru/mam_hyoo.git
pack lib git \https://github.com/hyoo-ru/mam_lib.git
```

Коли збірка зустрічає `$mol_view`, а теки `mol/` ще немає, вона шукає ім'я тут і клонує репозиторій. Нічого не вендориться й нічого не сплощується.

## Пакети

Тека верхнього рівня — це пакет, а пакет — це git-репозиторій. Ваш власний пакет просто тека, яку ви назвали: доки він живе локально, реєстрація йому не потрібна, а рядок `pack` знадобиться того дня, коли ви захочете отримувати його за іменем.

Пакети вкладаються один в одного. Пакет може нести власні оголошення `pack` для тек усередині себе, і MAM читає їх із `meta.tree` тієї теки, яка міститиме пакет. Цей сайт лежить у `bog/smalljs/` і сам є репозиторієм, переліченим у `bog/bog.meta.tree`, який, своєю чергою, міститься всередині чекауту `bog/` з кореневого `.meta.tree`.

### Один файл, потрібний кожному пакету

Пакету, який деплоїться, потрібен `.gitattributes` з єдиним рядком:

```
* -text
```

Це вимикає нормалізацію кінців рядків у git. Важливо це тому, що деплой означає коміт результату збірки в гілку, а результат не лише текст: цей сайт везе 57 бінарних файлів, шрифти, які він хостить у себе, і прев'ю-картинку для кожної сторінки. Нормалізовані на вході, до читача вони доїжджають побитими картинками й шрифтами, тоді як сама збірка лишається зеленою. У корені чекауту MAM лежить такий самий файл, де формати шрифтів додатково позначені `binary`.

Генератор пише його за вас; у репозиторій, який ви завели самі, додайте його руками.

## Модулі

Модуль — це тека, а тека — це компонент. Немає ані оператора імпорту, ані карти модулів: ім'я класу *і є* адресою, а кожне підкреслення в ньому роздільник тек:

```
$my_hello          →  my/hello/
$my_hello_form     →  my/hello/form/
$mol_button_major  →  mol/button/major/
$mol_after_frame   →  mol/after/frame/
```

У цьому все правило розв'язання імен. Складальник сканує ваш вихідний текст на токени `$name`, розбиває кожен по `_` і йде теками. Ніщо не оголошує залежність: оголошенням служить саме використання імені.

Практичний наслідок: **в іменах тек-модулів ніколи не буває підкреслення.** Теку `my/hello_form/` шукатимуть за шляхом `my/hello/form/` і не знайдуть — симптом у тому, що клас компілюється в редакторі, але відсутній у бандлі.

Модуль із підмодулями і сам може бути компонентом, в одній із двох форм. `$mol_button` лежить прямо в `mol/button/`, поруч із `major/` і `minor/`. `$mol_view` лежить на рівень глибше, у `mol/view/view/`, бо в `mol/view/` є ще `component/`, `selection/` і `tree2/`. MAM спершу пробує подвоєний шлях і відкочується до короткого, тож розв'язуються обидві розкладки.

## Файли в модулі

Будь-який файл необов'язковий. Модуль — це ті файли, які в ньому опинилися.

| Файл | Призначення |
|------|-------------|
| `hello.view.tree` | Декларативна розмітка |
| `hello.view.ts` | Поведінка: клас, що успадковує згенеровану базу |
| `hello.view.css.ts` | Типізовані стилі. Зверніть увагу на `.ts` на кінці: це TypeScript, що викликає `$mol_style_define`, а не таблиця стилів |
| `hello.ts` | Модуль зовсім без виду — моделі, утиліти, чиста логіка |
| `hello.test.ts` | Тести, які ганяє складальник |
| `hello.locale=ru.json` | Переклади; підхоплюється будь-який файл, що закінчується на `.locale=<lang>.json` |
| `hello.meta.tree` | Директиви збірки та деплою |
| `index.html` | Точка входу — потрібна лише модулю-застосунку |

Суфікс перед розширенням обмежує файл одним середовищем:

- `frame.web.ts` — тільки браузерний бандл, як `mol/after/frame/frame.web.ts`
- `build.node.ts` — тільки Node-бандл, як сам складальник MAM
- `hello.test.ts` — тільки тестові бандли

Складальник робить для кожного застосунку бандл `web` і бандл `node` і викидає файли, позначені для іншого, тож платформенному коду не доводиться захищатися в рантаймі.

Поруч із модулем приймаються й сирі файли `.css` — фреймворк використовує їх для тих небагатьох речей, які типізовані стилі виразити не можуть, як-от `@keyframes` і `content:`. Усе інше живе в `.view.css.ts`, де імена властивостей перевіряються.

## Згенеровані теки починаються з дефіса

MAM вважає ім'я вихідником, лише якщо воно починається з літери або цифри. Усе інше для збірки невидиме, тому кожна згенерована тека дістає префікс `-`: результат може лежати прямо поруч зі своїм входом, не потрапляючи назад на вхід. З тієї самої причини `.gitignore` робочого простору ігнорує `-*`.

**`-view.tree/`** з'являється поруч із будь-яким файлом `.view.tree` і зберігає те, у що компілюється дерево:

```
my/hello/-view.tree/
├── hello.view.tree.js            згенерований базовий клас
├── hello.view.tree.d.ts          його типізований інтерфейс
└── hello.view.tree.locale=en.json  видобуті @-рядки
```

Ваш `hello.view.ts` успадковує клас, що лежить там. У цьому й уся зв'язка між двома файлами — [Від TypeScript до view.tree](#!section=docs/page=from-ts-to-view-tree) розбирає згенерований код рядок за рядком.

**`-css/`** з'являється поруч із сирим файлом `.css` і зберігає згенерований `.ts`, який загортає таблицю стилів у виклик `$mol_style_attach`, щоб вона їхала разом із бандлом, а не потребувала `<link>`.

**`-/`** — результат збірки модуля, який ви зібрали. Для застосунку там лежать `web.js`, `web.css`, `web.audit.js`, `web.d.ts`, `web.deps.json`, по одному `web.locale=<lang>.json` на кожну мову, їхні `node`-двійники, переписаний `index.html`, а також згенеровані `package.json` і `manifest.json`. Саме цю теку ви деплоїте: опублікувати `app/-` на статичному хостингу і є весь деплой.

Нічого з цього не правиться руками. Складальник переписує ці файли щоразу, коли змінюється їхнє джерело, тож правка там зникне на наступному збереженні, і жодна помилка не пояснить чому. Змінюйте `.view.tree`, `.css` або вихідники й перезбирайте.

## Що насправді робить meta.tree

`meta.tree` — не маніфест пакета і залежності не перелічує: вони приходять із коду, де токен `$mol_view` уже є повним оголошенням. Він несе ту жменю речей, яку код не може сказати сам. `app/app.meta.tree` цього сайту — файл цілком:

```tree
include \/mol/offline/install
include \/bog/builderui/theme.css
deploy \/bog/smalljs/assets
```

- **`deploy \/path`** копіює файл або теку в `-/`, зберігаючи шлях відносно робочого простору: `\/bog/smalljs/assets` опиниться в `app/-/bog/smalljs/assets/`. Для статичних файлів, які деплой мусить везти, але які не імпортує жоден код: картинки, шрифти, іконки.
- **`include \/path`** і **`require \/path`** затягують модуль, на який ніхто не посилається, як-от `\/mol/offline/install`, чий увесь сенс — service worker, який він реєструє на завантаженні. Різняться вони лише порядком: `require` ставить модуль перед кодом, що його затягнув, `include` — після.
- **`pack <name> git \<url>`** — той самий запис реєстру, описаний вище; читається з meta-файла теки, яка міститиме пакет.

MAM читає в теці кожен файл `*.meta.tree`, тож ім'я не несе сенсу понад домовленість: `<module>.meta.tree` поруч із модулем, `.meta.tree` у корені робочого простору.

На практиці `deploy`, `include` і `require` належать модулю-застосунку, бо саме він збирається й деплоїться; звичайні компоненти виводять усе зі свого коду, і meta-файл їм не потрібен зовсім. Бібліотечний модуль дістає його, лише якщо в нього справді є незгадана залежність: `mol/assert/assert.meta.tree` складається з єдиного рядка `include \/mol/dev/format`, і це типовий розмір.
