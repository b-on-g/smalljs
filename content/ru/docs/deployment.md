# Деплой

Собранное $mol-приложение — это папка со статикой. Нечего запускать на сервере, нечего держать живым в Node, не из чего выбирать адаптер: где хостится папка, там работает и приложение.

## Что именно вы выкладываете

Сборка складывает всё в папку `-/` внутри модуля:

```
my/hello/-/
├── index.html                 переписан под адрес, по которому лежит сайт
├── web.js                     всё приложение, один файл
├── web.css
├── web.locale=en.json         по одному на язык
├── manifest.json
└── …                          всё, что притащила директива `deploy`
```

Эта папка и есть сайт. Отдайте её любым статическим хостингом — приложение заработает.

Всё остальное в `my/hello/` — исходники, а `-/` сгенерирована: корневой `.gitignore` игнорирует `-*`, так что результат сборки не попадает в историю самого проекта. В сеть он уезжает из ветки деплоя.

## Коротко

Воркфлоу пишет скаффолдер, поэтому новый проект публикуется по пушу:

```bash
npx create-view-tree-lsp my/hello
git push
```

`.github/workflows/deploy.yml` собирает модуль и пушит `my/hello/-/` в ветку `gh-pages`. GitHub отдаёт её, как только в **Settings → Pages → Source** выбрано *Deploy from a branch* и ветка `gh-pages` — а это и есть значение по умолчанию для репозитория, в котором такая ветка появилась. Если адрес отдаёт 404, проверять надо в первую очередь эту настройку.

Дальше сайт живёт по адресу `https://<user>.github.io/<repo>/`.

## Что делает воркфлоу

Всю работу тянут два экшена, и у каждого пара параметров:

```yaml
- uses: hyoo-ru/mam_build@master2
  with:
      package: "my/hello"     # какую папку собирать, путь от корня воркспейса
      modules: "app"          # какие модули внутри неё

- uses: hyoo-ru/gh-deploy@v4.4.1
  if: github.ref == 'refs/heads/main'
  with:
      folder: "my/hello/app/-"
```

`mam_build` разворачивает вокруг вашего пакета воркспейс MAM, превращает токены `$name` из кода в репозитории, где эти имена живут, и собирает. Ему не нужен ни лок-файл, ни шаг `npm install`: список зависимостей — это реестр в `.meta.tree`, как описано в [Структуре проекта](#!section=docs/page=structure).

`gh-deploy` коммитит собранную папку в `gh-pages`. Параметр `target-folder` кладёт её не в корень, а во вложенную папку — так и делается превью ветки:

```yaml
- name: Deploy feature branch
  if: startsWith(github.ref, 'refs/heads/feature/')
  uses: hyoo-ru/gh-deploy@v4.4.1
  with:
      folder: "my/hello/app/-"
      target-folder: ${{ github.ref_name }}
```

У каждой ветки `feature/*` появляется свой адрес на том же сайте, а триггер `delete` убирает папку, когда ветка удалена.

## Один файл, без которого деплой ломается

Пакету, который выкладывается, нужен рядом `.gitattributes` с единственной строкой:

```
* -text
```

Деплой — это коммит результата сборки в ветку, а в результате не только текст. Шрифты и картинки, нормализованные по дороге в этот коммит, приезжают к читателю битыми, при этом сама сборка остаётся зелёной. Скаффолдер этот файл пишет сам; в репозитории, заведённом руками, добавьте его руками.

## Файлы, которым место в корне сайта

`deploy \/path` в `meta.tree` копирует файл в `-/`, **сохраняя путь относительно воркспейса**. Для ассетов, на которые ссылается код, это правильно, а для файлов, которые хостинг ищет в корне, — нет. `CNAME`, `robots.txt`, страница подтверждения прав в поисковике: их копируют шагом воркфлоу после сборки и до шага деплоя.

```yaml
- name: Copy root-level files
  run: cp my/hello/public/CNAME my/hello/app/-/CNAME
```

## Глубокие ссылки на статике

Приложению с путевым роутингом (`/section=docs/page=views`, а не `#!section=docs`) от хостинга нужно одно: любой неизвестный путь внутри монтирования должен отдавать `index.html` приложения. Иначе первый заход по глубокой ссылке — это 404, и работают только переходы с главной.

У GitHub Pages нет правил переписывания, поэтому дорога лежит через его `404.html`: он отдаётся на любой неизвестный путь, и несколько строк внутри возвращают адрес в `index.html`, а роутер разворачивает его в настоящий маршрут. Копируется рядом с результатом сборки — тем же шагом, что и файлы выше.

Остальные хостинги говорят это одной строкой: `try_files $uri /index.html` в nginx, `try_files {path} /index.html` в Caddy, правило `/* /index.html 200` в Netlify.

Приложению на хеш-роутере (он по умолчанию) ничего из этого не нужно: всё, что после `#`, до сервера не доезжает.

## Проверить до пуша

Сборка одна и та же локально и в CI, поэтому зелёный аудит на машине означает зелёный деплой:

```bash
npx mam my/hello/app
cat my/hello/app/-/web.audit.js
```

`Audit passed` — это весь отчёт. Чтобы посмотреть на настоящий результат, отдайте папку любым статическим сервером:

```bash
npx serve my/hello/app/-
```

## Не только GitHub Pages

Ничего из написанного выше не привязано к GitHub. На выходе папка, деплой — это копирование. Netlify, Cloudflare Pages, S3 за CDN, nginx на VPS, docker-образ с этой папкой внутри: шаг сборки тот же `npx mam my/hello/app`, а заливаете вы `my/hello/app/-`.

Если нужна работа без сети, [Офлайн](#!section=docs/page=offline) добавляет service worker, кеширующий бандл, — и та же папка превращается в устанавливаемое приложение.
