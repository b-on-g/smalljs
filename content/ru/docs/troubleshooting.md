# Решение проблем

У каждой записи на этой странице одна и та же форма: сборка зелёная, аудит чистый, консоль молчит, а на экране пусто или не то, что вы задумывали. Компилятор этих ошибок не видит, потому что каждая из них — корректная программа, просто описывающая другой компонент. Найдите заголовок, похожий на то, что вы видите; под ним причина и лечение.

## Переопределение свойства ничего не делает, ошибки нет

Имя в `view.tree` и имя метода в классе разошлись, чаще всего регистром: `exchange_form` в дереве, `exchangeForm` в классе. Это два разных свойства. Классовое никто не вызывает, древесное остаётся со значением по умолчанию, и никто об этом не сообщает.

Имена везде `snake_case` и должны совпадать буква в букву. После правки `.view.ts` проверьте, что каждое переопределение по-прежнему называет существующее свойство; список для сверки — сгенерированный `-view.tree/*.view.tree.d.ts` рядом с деревом.

## Нужен placeholder, disabled или type у поля ввода

Это свойства `$mol_string`: `hint` — placeholder, `enabled` — выключенное состояние, `type` — тип поля. Задавайте их там, где поле используется:

```tree
<= Password $mol_string
	hint \Password
	type \password
	enabled <= can_edit true
	value? <=> password? \
```

Любое другое свойство любого другого компонента ищется так же: откройте его `.view.tree`, как показывает раздел [Как читать исходники](#!section=docs/page=mental-model/Docs.Body=%D0%9A%D0%B0%D0%BA%20%D1%87%D0%B8%D1%82%D0%B0%D1%82%D1%8C%20%D0%B8%D1%81%D1%85%D0%BE%D0%B4%D0%BD%D0%B8%D0%BA%D0%B8).

`attr *` нужен для настоящих DOM-атрибутов, которые компонент ещё не моделирует, и у него своя ловушка: блок, у которого первой строкой не идёт `^`, заменяет весь словарь атрибутов базы, так что написанный этак `$mol_button` теряет `disabled`, `role` и `tabindex`. Начните блок с `^`, чтобы унаследовать, а потом добавляйте свои ключи:

```tree
attr *
	^
	data_kind \primary
```

## Слово рендерится по буквам

Строку передали туда, где ожидается список, и её растащило по символам. Строки начинаются с `\`, списки — с `/`. Обычный случай — `sub`, это список:

```tree
sub / <= label \Hello
```

## Экран пустой, тесты зелёные

Переопределение выпало из `.view.ts`. Дерево даёт каждому свойству значение по умолчанию, поэтому, когда класс перестаёт переопределять `rows()`, TypeScript доволен, а список рендерится пустым. Тесты, проверяющие только модель, остаются зелёными, потому что с моделью всё в порядке.

На каждое переопределение, от которого зависит экран, пишите тест, читающий то, что видит пользователь: `rows()`, `sub()`, `title()` под-вью или DOM. [Тестирование](#!section=docs/page=testing) показывает и то, и другое.

## Данные не загружаются, компонент завис в состоянии загрузки

Метод с `@ $mol_mem` вернул промис в качестве значения: `fetch( uri ).then( ... )`, `async`-метод или результат `$mol_wire_async( this ).load()`. Промис в ячейке читается всеми как «всё ещё вычисляется», а когда он разрешается, ячейка пересчитывается и выдаёт свежий промис. Сеть работает, вью результата не видит никогда.

Правильная форма синхронная: вызовите `this.$.$mol_fetch.json( uri )` внутри ячейки и верните разобранное значение. Фибра приостановится, пока не придёт ответ, и перезапустит ячейку, так что промис в вашем коде не появляется вовсе. Там, где асинхронная работа всё-таки должна происходить в стороне, кладите её результат в отдельную ячейку состояния, а эффект пусть возвращает флаг или ключ, но не промис.

Вторая причина — проглоченная ошибка: `try`/`catch` внутри ячейки, который ловит приостановку заодно с настоящими сбоями. Перебрасывайте всё, что является `Promise`, или пользуйтесь `$mol_fail_catch`, который делает эту проверку за вас.

## Циклическая подписка

Метод с `@ $mol_mem` записал в другую ячейку или выполнил побочный эффект, который в итоге инвалидировал что-то им же прочитанное. Вычисления только читают и возвращают; записи, сеть, таймеры и DOM — дело обработчиков с `@ $mol_action`. Второй источник того же сообщения — связывание `<=>` с ребёнком вместе с методом в классе, который делегирует этому же ребёнку, о чём следующая запись.

## Maximum call stack

Это дают две конструкции. Первая: в дереве у ребёнка `tab? <=> tab?`, а в классе `tab() { return this.Head().tab() }` — ребёнок спрашивает владельца, владелец спрашивает ребёнка. Уберите `<=>` к тому ребёнку, которому делегируете.

Вторая: под-вью ре-типизировали в собственный класс, а класс зовёт `super` у свойства, перечисленного в дереве. Этот `super` — не базовая реализация, а заглушка, сгенерированная деревом для перечисленного связывания, и заглушка делегирует обратно владельцу. Делегируйте исходной реализации явно, см. запись про ре-типизацию ниже.

## Значение с большой буквы не переопределяется из TypeScript

`<= Label* \` порождает метод с именем `Label`, а `label()` в классе — это другой метод. Под-вью пишутся с большой буквы, значения — с маленькой, и регистр в дереве определяет имя сгенерированного метода.

## Все строки вложенного списка показывают один и тот же элемент

Ключевое под-вью внутри другого ключевого под-вью не получает своего ключа. `Cell*0` внутри `Row*0` рендерится с ключом `0` в каждой строке. Вынесите строку в отдельный компонент и передавайте её данные через свойства, а внешнее вью ключуйте как `Row*`, а не `Row*0`.

## Поменял класс под-вью, и содержимое пропало

Ре-типизация `Pre* $mol_text_code` в `Pre* $my_code` теряет связывания, которые для него объявляло базовое дерево, так что их надо перечислить заново. А перечисление `text <= pre_text* \` создаёт пустую заглушку, которая шадовит настоящий `pre_text` у `$mol_text`. Делегируйте в классе вместо того, чтобы полагаться на `super`, — `super` и есть эта заглушка:

```typescript
pre_text( index: number ) {
	return $mol_text.prototype.pre_text.call( this, index )
}
```

## Методы из view.ts базового компонента не видны в наследнике

`$my_child $my_base` в дереве наследует класс, сгенерированный из `base.view.tree`, а не тот, что вы написали в `base.view.ts`. Определённые там методы до ребёнка не доходят, и TypeScript сообщает, что их нет. Логика, общая для нескольких вью, живёт в обычном `.ts`-файле в `namespace $`, без дерева — так написан и сам `$mol_view`.

## Базовый компонент из того же файла view.tree теряет поведение

Когда в одном файле дерева объявлены и база, и наследующий её класс, тело `.view.ts` базы для ребёнка пропускается. Базе, у которой есть `.view.ts`, дайте отдельную папку.

## Стили протекают между под-вью и компонентом внутри него

`Nav $my_app_nav` внутри `$my_app` вешает один и тот же атрибут `my_app_nav` и на под-вью, и на компонент, и один селектор попадает в оба. Назовите под-вью так, чтобы имя не повторяло хвост класса, например `Nav_row`.

## Селектор по атрибуту со значением false никогда не срабатывает

Булев атрибут со значением `false` с элемента снимается, поэтому `[expanded="false"]` не совпадает ни с чем. Условный рендеринг — не работа для CSS; переопределите фабрику под-вью и верните `null` для того варианта, где такого вью нет.

## Число в стилях ничего не меняет

Каждому числу в `style *` дописывается `px`: `flexGrow 1` превращается в `flex-grow: 1px`, который браузер выбрасывает. Безразмерные значения пишите строками, `flexGrow \1`.

## Два ребёнка скролла лежат друг на друге

`$mol_scroll` держит ровно одного ребёнка. Заверните детей в `$mol_view` или `$mol_list` и отдайте скроллу его.

## minimal_height ни на что не влияет

`minimal_height` — это число, по которому виртуализированный `$mol_list` прикидывает строки до их рендеринга; высоту оно не задаёт. Высота задаётся в `.view.css.ts`.

## Встроенный компонент распирает страницу вбок

Вью, смонтированное внутри чужой вёрстки, по умолчанию не сжимается уже своего содержимого. Задайте корню `minWidth: 0` в стилях, чтобы его можно было сдавить, как соседние элементы.

## Сторонний CSS не стилизует компонент

Компонент без `dom_name` рендерится элементом, названным по своему классу, а для CSS-фреймворка это неизвестный строчный элемент. Задайте тег явно: у `$mol_button` его нет, поэтому кнопке, которую должен стилизовать внешний CSS, нужен `dom_name \button`.

## Клик по ссылке на текущую страницу очищает URL

`$mol_link` с `arg *` работает как переключатель: на странице, чей URL уже совпадает, клик эти ключи убирает. Для ссылки, которая только переходит, унаследуйтесь от неё с `uri_off <= uri`. Чтобы кликом перезагрузить тот же маршрут, вызовите `$mol_state_arg.value()` из обработчика и сделайте событию `preventDefault`.

## Обработчик поля ввода срабатывает на каждый рендер

У `prop?`, который вы добавили в наследника `$mol_string`, имя свойства, уже используемого базой: `enter`, `submit`, `hint`, `value`, `keyboard`. Сверяйте новые имена с базовым деревом, прежде чем их добавлять.

## Исключение из сеттера значения нигде не показывается

`$mol_string` ловит исключение из `value?` и отдаёт его в `setCustomValidity` поля, поэтому оно проявляется только как нативная валидация формы. Сообщайте об ошибке своим каналом — строкой состояния или под-вью с сообщением.

## Ключевое связывание обработчика ругается, что метода нет

`event_click? <=> pick*? null` на ключевом под-вью не порождает заглушку для `pick`. Объявите его в корне дерева сами, `pick*? null`, и реализуйте в классе.

## В бандле оказался модуль, который я не использую

Сборщик ищет зависимости, сканируя исходный текст на токены вида `$mol_name`, и токен в строковом литерале или в doc-комментарии `/** */` считается наравне с токеном в коде. Имя, упомянутое в doc-комментарии как пример, тащит за собой весь свой модуль, а вылезает это в файле, которого вы не касались. Пишите примеры и заметки без приставки `$` или называйте папку.

## Дальше

Почти всё это сводится к одному правилу: имя в дереве — это контракт, а компилятор проверяет типы, но не имена. [Ментальная модель](#!section=docs/page=mental-model) объясняет, почему дерево — это список переопределений, а [Тестирование](#!section=docs/page=testing) показывает тест, который ловит молчаливые случаи.
