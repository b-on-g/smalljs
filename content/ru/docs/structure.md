# Структура проекта

У $mol-проекта четыре вложенных уровня: **воркспейс**, который вы склонировали, **пакеты** внутри него, **модули** внутри пакетов и **файлы** внутри модуля. Раскладка отвечает на один практический вопрос — куда класть новый проект и кому принадлежит его история, — и почти всё, что делает сборка, следует из неё.

```structure
mam/                         воркспейс — склонированный MAM
├── .meta.tree               реестр: какой пакет из какого репозитория
├── mol/                     пакет — сам фреймворк, свой git-репозиторий
└── my/                      пакет — ваш, ваш git-репозиторий
    ├── .gitattributes       сохраняет собранные бинарники целыми
    ├── my.meta.tree         реестр ваших проектов
    └── hello/               проект — модуль и свой git-репозиторий
        ├── index.html       точка входа (только у модулей-приложений)
        ├── hello.view.tree  разметка
        └── form/            подмодуль — $my_hello_form
```

На этой странице у каждой строки листинга есть вопросик с причиной, по которой она здесь; разделы ниже говорят то же самое подробно.

## Как завести проект

Пять шагов. Повторяется только первый, а последние три за вас может сделать скаффолдер.

**1. Склонируйте воркспейс, один раз.** Всё, что вы напишете дальше, живёт внутри него.

```bash
git clone https://github.com/hyoo-ru/mam.git
cd mam
```

**2. Заведите свой пакет.** Одна короткая папка — ваше имя, ваша компания, ваш ник — и свой git-репозиторий. Это контейнер для всех проектов, которые вы начнёте:

```bash
mkdir my
cd my
git init
```

Выложите его туда, где держите код, публично или приватно. Заодно положите рядом `.gitattributes` с единственной строкой `* -text`; зачем — в разделе про пакеты ниже.

**3. Добавьте реестр.** `my/my.meta.tree` — список проектов внутри вашего пакета. Он начинается пустым и получает по строке на проект:

```tree
pack hello git \https://github.com/you/hello.git
```

MAM читает его ровно так же, как корневой `.meta.tree` уровнем выше, поэтому коллега, склонировавший `my/`, получит и проекты.

**4. Создайте проект со своим репозиторием.** Папка и есть компонент — `my/hello/` это `$my_hello`, — а история принадлежит ему, а не вашему пакету и не $mol:

```bash
mkdir hello
cd hello
git init
```

В этом разделении и смысл раскладки: коммит в `my/hello/` уходит в репозиторий `hello`, никогда не в `my` и не в `mol`.

**5. Пропишите его.** Добавьте строку `pack` из шага 3 в `my/my.meta.tree` — и свежий чекаут вашего пакета подтянет проект по имени.

[Скаффолдер](#!section=docs/page=tooling) напишет рабочий модуль за вас в любой момент после второго шага:

```bash
npx create-view-tree-lsp my/hello
```

## Воркспейс

MAM клонируют один раз и работают внутри него. Это не папка, куда копируются зависимости: каждый пакет лежит там своим git-чекаутом, с историей, так что вы можете читать исходники фреймворка, поставить в них `debugger` и открыть pull request из той же рабочей копии.

Корневой `.meta.tree` — реестр, который это обеспечивает:

```tree
pack mol git \https://github.com/hyoo-ru/mam_mol.git
pack hyoo git \https://github.com/hyoo-ru/mam_hyoo.git
pack lib git \https://github.com/hyoo-ru/mam_lib.git
```

Когда сборка встречает `$mol_view`, а папки `mol/` ещё нет, она ищет имя здесь и клонирует репозиторий. Ничего не вендорится и ничего не уплощается.

## Пакеты

Папка верхнего уровня — это пакет, а пакет — это git-репозиторий. Ваш собственный пакет просто папка, которую вы назвали: пока он живёт локально, регистрация ему не нужна, а строка `pack` понадобится в тот день, когда вы захотите получать его по имени.

Пакеты вкладываются друг в друга. Пакет может нести собственные объявления `pack` для папок внутри себя, и MAM читает их из `meta.tree` той папки, которая будет содержать пакет. Этот сайт лежит в `bog/smalljs/` и сам является репозиторием, перечисленным в `bog/bog.meta.tree`, который, в свою очередь, находится внутри чекаута `bog/` из корневого `.meta.tree`.

### Один файл, который нужен каждому пакету

Пакету, который деплоится, нужен `.gitattributes` с единственной строкой:

```
* -text
```

Это выключает нормализацию концов строк в git. Важно потому, что деплой означает коммит результата сборки в ветку, а результат — не только текст: этот сайт везёт 57 бинарных файлов, шрифты, которые он хостит у себя, и превью-картинку для каждой страницы. Нормализованные на входе, до читателя они доезжают битыми картинками и шрифтами, при том что сама сборка остаётся зелёной. В корне чекаута MAM лежит такой же файл, где форматы шрифтов дополнительно помечены `binary`.

Генератор пишет его за вас; в репозиторий, который вы завели сами, добавьте его руками.

## Модули

Модуль — это папка, а папка — это компонент. Нет ни оператора импорта, ни карты модулей: имя класса *и есть* адрес, а каждое подчёркивание в нём разделитель папок:

```
$my_hello          →  my/hello/
$my_hello_form     →  my/hello/form/
$mol_button_major  →  mol/button/major/
$mol_after_frame   →  mol/after/frame/
```

В этом всё правило разрешения имён. Сборщик сканирует ваш исходный текст на токены `$name`, разбивает каждый по `_` и идёт по папкам. Ничто не объявляет зависимость: объявлением служит само использование имени.

Практическое следствие: **в именах папок-модулей никогда не бывает подчёркивания.** Папку `my/hello_form/` будут искать по пути `my/hello/form/` и не найдут — симптом в том, что класс компилируется в редакторе, но отсутствует в бандле.

Модуль с подмодулями и сам может быть компонентом, в одной из двух форм. `$mol_button` лежит прямо в `mol/button/`, рядом с `major/` и `minor/`. `$mol_view` лежит на уровень глубже, в `mol/view/view/`, потому что в `mol/view/` есть ещё `component/`, `selection/` и `tree2/`. MAM сперва пробует удвоенный путь и откатывается к короткому, так что разрешаются обе раскладки.

## Файлы в модуле

Любой файл необязателен. Модуль — это те файлы, которые в нём оказались.

| Файл | Назначение |
|------|------------|
| `hello.view.tree` | Декларативная разметка |
| `hello.view.ts` | Поведение: класс, наследующий сгенерированную базу |
| `hello.view.css.ts` | Типизированные стили. Обратите внимание на `.ts` на конце: это TypeScript, вызывающий `$mol_style_define`, а не таблица стилей |
| `hello.ts` | Модуль вообще без вью — модели, утилиты, чистая логика |
| `hello.test.ts` | Тесты, которые гоняет сборщик |
| `hello.locale=ru.json` | Переводы; подхватывается любой файл, оканчивающийся на `.locale=<lang>.json` |
| `hello.meta.tree` | Директивы сборки и деплоя |
| `index.html` | Точка входа — нужна только модулю-приложению |

Суффикс перед расширением ограничивает файл одним окружением:

- `frame.web.ts` — только браузерный бандл, как `mol/after/frame/frame.web.ts`
- `build.node.ts` — только Node-бандл, как сам сборщик MAM
- `hello.test.ts` — только тестовые бандлы

Сборщик делает для каждого приложения бандл `web` и бандл `node` и выбрасывает файлы, помеченные для другого, так что платформенному коду не приходится защищаться в рантайме.

Рядом с модулем принимаются и сырые файлы `.css` — фреймворк использует их для тех немногих вещей, которые типизированные стили выразить не могут, вроде `@keyframes` и `content:`. Всё остальное живёт в `.view.css.ts`, где имена свойств проверяются.

## Сгенерированные папки начинаются с дефиса

MAM считает имя исходником, только если оно начинается с буквы или цифры. Всё прочее для сборки невидимо, потому каждая сгенерированная папка получает префикс `-`: результат может лежать прямо рядом со своим входом, не попадая обратно на вход. По той же причине `.gitignore` воркспейса игнорирует `-*`.

**`-view.tree/`** появляется рядом с любым файлом `.view.tree` и хранит то, во что компилируется дерево:

```
my/hello/-view.tree/
├── hello.view.tree.js            сгенерированный базовый класс
├── hello.view.tree.d.ts          его типизированный интерфейс
└── hello.view.tree.locale=en.json  извлечённые @-строки
```

Ваш `hello.view.ts` наследует лежащий там класс. Это и есть вся связь между двумя файлами — [От TypeScript к view.tree](#!section=docs/page=from-ts-to-view-tree) разбирает сгенерированный код построчно.

**`-css/`** появляется рядом с сырым файлом `.css` и хранит сгенерированный `.ts`, который заворачивает таблицу стилей в вызов `$mol_style_attach`, чтобы она ехала вместе с бандлом, а не требовала `<link>`.

**`-/`** — результат сборки модуля, который вы собрали. Для приложения там лежат `web.js`, `web.css`, `web.audit.js`, `web.d.ts`, `web.deps.json`, по одному `web.locale=<lang>.json` на каждый язык, их `node`-двойники, переписанный `index.html`, а также сгенерированные `package.json` и `manifest.json`. Именно эту папку вы деплоите: опубликовать `app/-` на статическом хостинге и есть весь деплой.

Ничего из этого не правится руками. Сборщик переписывает эти файлы каждый раз, когда меняется их источник, так что правка там исчезнет на следующем сохранении, и никакая ошибка не объяснит почему. Меняйте `.view.tree`, `.css` или исходники и пересобирайте.

## Что на самом деле делает meta.tree

`meta.tree` — не манифест пакета и зависимости не перечисляет: они приходят из кода, где токен `$mol_view` уже является полным объявлением. Он несёт ту горстку вещей, которую код не может сказать сам. `app/app.meta.tree` этого сайта — файл целиком:

```tree
include \/mol/offline/install
include \/bog/builderui/theme.css
deploy \/bog/smalljs/assets
```

- **`deploy \/path`** копирует файл или папку в `-/`, сохраняя путь относительно воркспейса: `\/bog/smalljs/assets` окажется в `app/-/bog/smalljs/assets/`. Для статических файлов, которые деплой обязан везти, но которые не импортирует никакой код: картинки, шрифты, иконки.
- **`include \/path`** и **`require \/path`** затягивают модуль, на который никто не ссылается, вроде `\/mol/offline/install`, чей весь смысл — service worker, который он регистрирует при загрузке. Различаются они только порядком: `require` ставит модуль перед кодом, который его затянул, `include` — после.
- **`pack <name> git \<url>`** — та самая запись реестра, описанная выше; читается из meta-файла папки, которая будет содержать пакет.

MAM читает в папке каждый файл `*.meta.tree`, так что имя не несёт смысла сверх соглашения: `<module>.meta.tree` рядом с модулем, `.meta.tree` в корне воркспейса.

На практике `deploy`, `include` и `require` относятся к модулю-приложению, потому что именно оно собирается и деплоится; обычные компоненты выводят всё из своего кода, и meta-файл им не нужен вовсе. Библиотечный модуль получает его, только если у него действительно есть неупомянутая зависимость: `mol/assert/assert.meta.tree` состоит из единственной строки `include \/mol/dev/format`, и это типичный размер.
