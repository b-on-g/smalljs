# Тестирование

Вью в $mol — функция от своего состояния, и это меняет то, как выглядит тест. Пользовательский сценарий пишется вызовами собственных методов вью: задать черновик, выполнить действие, прочитать то, что увидел бы пользователь.

```typescript
app.draft( 'Milk' )
app.add()
$mol_assert_equal( app.item_title( 0 ), 'Milk' )
```

Ни селекторов, ни браузера, ни Playwright с Cypress, ни ожидания чего бы то ни было. Тот же файл даёт вам ещё и вот что:

- **Скорость.** Тесты выполняются в Node за миллисекунды; тысяча штук укладывается примерно в минуту. `node my/hello/-/node.test.js` гоняет тесты одного модуля.
- **Нулевую настройку.** Файл `hello.test.ts` рядом с компонентом подхватывается сборщиком и компилируется в `-/node.test.js`. Непрерывная интеграция на `mam_build` гоняет его и роняет сборку, когда тест падает.
- **Подмену сервисов через контекст.** У каждого теста свой `$`, и всё, до чего компонент дотягивается через `this.$.X`, подменяется присваиванием дублёра в этот `$`. Ровно поэтому надо писать `this.$.$mol_fetch`, а не `$mol_fetch`: первое заменяемо, второе — нет.
- **Замоканное время.** Таймеры, созданные через контекст, сами не тикают; `$mol_after_mock_warp()` выполняет всё, что в очереди.
- **Настоящий DOM, когда он нужен.** В Node-бандле едет jsdom, поэтому `dom_node()` и `querySelectorAll` работают в том же тестовом файле.

## Сценарий через методы вью

Возьмём список дел из [Сборника рецептов](#!section=docs/page=cookbook): строка `draft?`, список `items`, действие `add` и действие `delete`. Его тест живёт в `my/todo/todo.test.ts`:

```typescript
namespace $ {
	$mol_test({

		'add an item and delete it'( $ ) {
			const app = $my_todo.make({ $ })

			app.draft( 'Milk' )
			app.add()
			$mol_assert_equal( app.items().length, 1 )
			$mol_assert_equal( app.item_title( 0 ), 'Milk' )
			$mol_assert_equal( app.draft(), '' )

			app.delete( 0 )
			$mol_assert_like( app.item_rows(), [] )
		},

		'blank draft adds nothing'( $ ) {
			const app = $my_todo.make({ $ })

			app.draft( '   ' )
			app.add()
			$mol_assert_like( app.items(), [] )
		},

	})
}
```

На что стоит обратить внимание:

- Тестовый файл использует `namespace $`, а не `$.$$`. Контекст `$` приходит аргументом, свежий на каждый тест, а компонент создаётся через `Klass.make({ $ })`, чтобы читать сервисы из этого контекста.
- Клик — это вызов обработчика. `app.add()` — то, что делает кнопка; `app.Add().click( event )` идёт тем же путём, когда вы хотите захватить и связывание.
- Проверяйте то, что видит пользователь: `items()`, `item_rows()`, `sub()`, `title()` под-вью. Модель, проверенная через экран, заодно ловит переопределение, выпавшее из класса, чего тест одной только модели не заметит.
- `$mol_assert_equal` сравнивает по идентичности, `$mol_assert_like` сравнивает структуру, `$mol_assert_fail( ()=> ..., 'message' )` ожидает исключения.
- Имя теста и есть описание. Комментариев в теле нет.

## Мок сервиса

Каждый тест получает свежий контекст, производный от глобального. Присвойте сервису в этом `$` наследника до создания компонента — и каждое `this.$.X` внутри компонента разрешится в подмену. Вот дублёр fetch для компонента `$my_users` из [Загрузки данных](#!section=docs/page=data):

```typescript
namespace $ {
	$mol_test({

		'user names come from the response'( $ ) {
			$.$mol_fetch = class extends $.$mol_fetch {
				static override json( input: RequestInfo ) {
					if( String( input ).endsWith( '/users' ) ) return [ { id: 1, name: 'Ada' } ]
					return $mol_fail( new Error( 'Unexpected request: ' + input ) )
				}
			}
			const app = $my_users.make({ $ })
			$mol_assert_like( app.user_names(), [ 'Ada' ] )
		},

	})
}
```

`users()` в компоненте вызывает `this.$.$mol_fetch.json( ... )`, поэтому запрос уходит в мок, а значение доступно синхронно, без всякого ожидания. Если бы компонент вызвал глобальный `$mol_fetch.json( ... )`, мока бы никто не спросил. Встроенные моки и так подменяют в контексте глобальные `fetch` и `XMLHttpRequest` прокси-объектами, которые бросают исключение, так что запрос, проскочивший мимо контекста, падает громко, а не лезет в сеть.

Тот же приём покрывает `$mol_state_arg` для URL, `$mol_state_local` для хранилища и всё остальное, что компонент берёт из `this.$`.

Есть ещё `$mol_test_mocks` — список функций, которые прогоняются по контексту перед каждым тестом в бандле, включая тесты других модулей. Это место для правил, верных везде, — так фреймворк регистрирует собственные моки: дублёр хранилища, который запоминает всё, что ему дали, локаль, возвращающая пустой словарь, запрет на сеть из абзаца выше. Фикстурам одного компонента там не место.

## Время

Собственные тесты фреймворка регистрируют моки для `$mol_after_timeout`, `$mol_after_frame` и их родни, и эти моки есть и в вашем бандле. Таймер, созданный через `new this.$.$mol_after_timeout( ms, task )`, попадает в очередь вместо планирования, а `$mol_after_mock_warp()` эту очередь выполняет. Пусть есть тост, который прячется сам:

```typescript
@ $mol_mem toast( next?: string ) { return next ?? '' }

@ $mol_action notify( text: string ) {
	this.toast( text )
	new this.$.$mol_after_timeout( 3000, ()=> this.toast( '' ) )
}
```

тогда тест двигает время руками:

```typescript
'toast hides after the timer'( $ ) {
	const app = $my_greeter.make({ $ })
	app.notify( 'Saved' )
	$mol_assert_equal( app.toast(), 'Saved' )
	$mol_after_mock_warp()
	$mol_assert_equal( app.toast(), '' )
},
```

Голый `setTimeout` во вью не мокается и переживает тест; это одна из причин создавать таймеры через контекст.

## Через DOM

В Node-бандле `$mol_dom_context` — это окно jsdom, поэтому вью рендерится в настоящие элементы. Пользуйтесь этим, когда проверка про разметку, а не про состояние:

```typescript
'greets by name'( $ ) {
	const app = $my_greeter.make({ $ })
	app.name( 'Ada' )
	$.$mol_dom_context.document.body.appendChild( app.dom_node() )
	app.dom_tree()
	$mol_assert_equal( app.Hello().dom_node().textContent, 'Hello, Ada!' )
	app.destructor()
},
```

`dom_node()` создаёт элемент, `dom_tree()` рендерит поддерево, а `destructor()` освобождает вью, чтобы его ячейки не пережили тест. Атрибут, который под-вью получает от своего имени, здесь `[my_greeter_hello]`, и есть селектор, когда `querySelector` вам милее вызова под-вью.

В jsdom нет двух глобальных объектов, за которыми лезут поля ввода и жесты, — `ShadowRoot` и `PointerEvent`. Отрендеренный без них `$mol_string` пишет в лог `ReferenceError` и остаётся пустым, пока остальное дерево рендерится. Одолжите их у окна jsdom; это правило без всяких данных, общее для каждого теста, поэтому ему место в `$mol_test_mocks`:

```typescript
$mol_test_mocks.push( $ => {
	const win = $.$mol_dom_context
	Object.assign( globalThis, {
		ShadowRoot: win.ShadowRoot,
		PointerEvent: win.PointerEvent ?? win.MouseEvent,
	} )
} )
```

## Чего Node-тест не покрывает

Геометрию и оформление. Ложатся ли два блока в ряд, вылезает ли панель за экран, читается ли тёмная тема — ничего этого в jsdom нет. Для вёрстки, которую вы трогали, откройте `-/test.html` модуля в браузере — он монтирует приложение и гоняет там те же тесты — и посмотрите глазами.

## Заметки из практики

- **Тишина — это падение.** Тест, завалившийся на проверке, и зависший тест выглядят одинаково: вывода нет, процесс жив. Ищите `All tests passed` в конце; если этой строки нет, начинайте с последней проверки. Асинхронный тест ограничен одной секундой.
- **Сломайте один нарочно.** Когда прогон ничего не печатает, переверните проверку и убедитесь, что падение видно. Набор тестов, который не умеет падать, ничего не измеряет.
- **Не проверяйте локализованные строки.** Значения, помеченные в дереве через `@`, разрешаются через локаль, а она в каждом свежем контексте прогревается заново. Проверяйте структуру, а не текст подписи.
