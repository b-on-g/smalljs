# Инструментарий

$mol работает в любом редакторе, но небольшой набор инструментов делает `.view.tree` и типизированные стили гораздо удобнее: генератор проектов, языковой сервер, интеграции с редакторами Zed и VS Code, а также скилл, который учит LLM-ассистентов фреймворку.

## Генерация проекта

`create-view-tree-lsp` создаёт готовый к запуску модуль $mol, чтобы вам не собирать шаблонный код вручную:

```bash
npx create-view-tree-lsp bog/myapp
```

Запускать из корня своей копии MAM: пути модулей отсчитываются оттуда, там же проекту и жить. Вне воркспейса команда предупредит, а не оставит выяснять это на первой сборке.

Аргумент — путь модуля (`namespace/name` или эквивалентное `bog_myapp`). Он записывает `view.tree`, `view.ts`, `view.css.ts` и `index.html` для работающего приложения, плюс GitHub Actions для его деплоя.

Всё, что генератор умеет положить, кладётся по умолчанию. Вы называете только то, чего не хотите:

```bash
npx create-view-tree-lsp bog/myapp --no-tauri --no-backend
```

- `--no-baza` — local-first хранилище **Гипер База**
- `--no-docker` — настройка **Docker** с `docker-compose.yml` и конфигом nginx
- `--no-tauri` — десктопная оболочка **Tauri**
- `--no-backend` — REST-бэкенд `$mol_server` с хранилищем `node:sqlite` и общим типом элемента на TypeScript
- `--no-prerender`, `--no-seo` — видимость для поисковиков, описанная ниже в разделе [Непрерывная интеграция](#!section=docs/page=tooling/Docs.Body=%D0%9D%D0%B5%D0%BF%D1%80%D0%B5%D1%80%D1%8B%D0%B2%D0%BD%D0%B0%D1%8F%20%D0%B8%D0%BD%D1%82%D0%B5%D0%B3%D1%80%D0%B0%D1%86%D0%B8%D1%8F)

Незнакомый флаг обрывает запуск, так что опечатка не оставит в проекте лишнего молча.

Генератор — это тонкая обёртка над CLI языкового сервера, так что `npx view-tree-lsp create bog/myapp` делает то же самое напрямую.

## Переводы

Переводы лежат рядом со своим модулем, в `<модуль>/<имя>.locale=<lang>.json`. Коду так удобно, переводчику — нет: вместо одного списка фраз он получает тридцать мелких файлов.

**[$yuf_localizer](https://zerkalica.github.io/yuf/#!demo=yuf_localizer_demo)** закрывает этот разрыв. Укажите ему адреса проектов и коды языков — и он покажет все ключи одним списком с поиском, отмечая те, до которых ещё не дошли руки: ключи, которые есть только по-английски, изменённые, но не зафиксированные, и устаревшие, которых в проекте уже нет. Переводы держатся в браузере, пока вы их не выгрузите, так что между заходами ничего не теряется.

Когда переводчик закончил, выгрузите результат и разложите его обратно по модулям:

```bash
# из корня MAM
npx view-tree-lsp locale bog/myapp/app/- --exclude=mol --update
```

Аргументом можно дать и папку, и отдельный файл локали. Флаги:

- `--include=` принимает кусок пути и оставляет только модули, чей путь его содержит; повторять можно сколько угодно раз
- `--exclude=` наоборот пропускает такие — `--exclude=mol` оставит пакеты самого фреймворка нетронутыми
- `--update` дописывает в существующие файлы: значения из источника побеждают, а ключи, которых в нём нет, остаются
- `--dry` показывает план и ничего не записывает

Ключ несёт путь к своему модулю, поэтому `$my_page_greeting` попадёт в `my/page/page.locale=ru.json` — рядом с исходниками, которым принадлежит. А вот вычислить этот модуль сложнее, чем кажется: `_` разделяет и папки, и слова, так что «самый длинный совпавший путь» — неверный ответ. В `$my_page_lang_hint` свойство начинается на `lang`, и настоящий соседний подмодуль `my/page/lang` забрал бы ключ себе. Поэтому команда спрашивает у каждого кандидата, какие ключи он объявил — MAM записывает ровно их в его файл локали в `-view.tree`, — и отдаёт ключ владельцу.

## Непрерывная интеграция

Генератор записывает GitHub Actions в `.github/workflows/`, так что новый проект деплоится и релизится без дополнительной настройки.

`deploy.yml` запускается на каждый push. Он собирает приложение с помощью `hyoo-ru/mam_build`, публикует `app/-` в **GitHub Pages** из `main` и даёт каждой ветке `feature/*` свою папку предпросмотра — она удаляется автоматически, когда ветку удаляют.

### SEO

Оба включены по умолчанию и оба срабатывают по тегам `v*`:

- **`--no-prerender`** убирает шаг, который рендерит перечисленные вами экраны (например, `home`) в статический HTML через `b-on-g/mol-prerender-action` — то самое, благодаря чему краулеры и превью ссылок видят настоящий контент.
- **`--no-seo`** убирает рантайм `$bog_seo`: роутер по pathname с картой сайта, `robots.txt`, `llms.txt` и внедрением метаданных на каждую страницу. Задача обслуживает сборку, выгружает канонический предрендеренный HTML и заворачивает его обратно в деплой.

Они делают одно и то же и пишут в одну папку, поэтому в `deploy.yml` попадает только один: `$bog_seo`, пока он включён, и prerender-action, как только вы передали `--no-seo`. Оставляйте `$bog_seo`, когда нужны карты сайта и метаданные на каждую страницу, и спускайтесь к prerender-action, когда вся работа — горстка публичных экранов.

### Десктоп Tauri

С опцией Tauri `tauri.yml` собирает десктопные бинарники по тегам `v*` (или по запросу) через переиспользуемый воркфлоу `b-on-g/tauri-mol-workflow-template`, из того же модуля, что вы деплоите в веб.

## Языковой сервер

`view-tree-lsp` — это реализация Language Server Protocol для формата `view.tree`. Запускайте его по требованию через npx, без глобальной установки:

```bash
npx view-tree-lsp@latest
```

Он сканирует ваше рабочее пространство и даёт любому редактору с поддержкой LSP:

- автодополнение для компонентов `$mol_*` и компонентов и свойств, определённых в вашем собственном проекте
- подсказки свойств в рамках компонента под курсором
- структуру объявлений компонентов для навигации
- живые обновления по мере изменения файлов

Поскольку он говорит на LSP, вы можете направить language-client любого редактора на `npx view-tree-lsp`. Две интеграции ниже настраивают его за вас.

## Zed

Расширение **View Tree Syntax Highlighting for $mol** объединяет грамматику tree-sitter, языковой сервер и опциональную тему иконок. Установите его из менеджера расширений Zed:

1. Откройте палитру команд (`Cmd+Shift+P` / `Ctrl+Shift+P`)
2. Выполните **zed: extensions**
3. Найдите `view.tree` или `mol` и установите расширение

Вы получаете подсветку синтаксиса, автодополнение и структуру для файлов `.view.tree`. [Исходники](https://github.com/Dev-cmyser/zed-view.tree-mol-support) и соответствующая [тема иконок](https://github.com/Dev-cmyser/zed-viewtree-icon-theme) на GitHub.

## VS Code

Рабочее пространство MAM уже несёт свою настройку VS Code. Когда вы открываете склонированную папку `mam`, VS Code предлагает установить рекомендованные расширения из `.vscode/extensions.json`:

- `nin-jin.vscode-language-tree` — поддержка языка `view.tree`
- `stan-donarise.view-tree-language` — синтаксис и грамматика
- `editorconfig.editorconfig` — единообразное форматирование

Та же папка поставляет `mol.code-snippets`, так что сниппеты компонентов и биндингов доступны без всякой дополнительной настройки. Примите предложение — и файлы `.view.tree` и TypeScript подсвечиваются из коробки.

## Скилл для LLM

`mol_skill` даёт AI-ассистенту контекст, нужный, чтобы писать на $mol: синтаксис `view.tree`, устройство MAM-модуля, разделение между `view.ts` и `view.css.ts`, моделирование данных в Гипер Базе и упаковку в Tauri. Это обычная папка со скиллом — воркфлоу `SKILL.md` плюс справочники, так что подхватить его может любой LLM-инструмент, читающий формат skills, включая Claude Code и Cursor. Установка через CLI skills:

```bash
npx skills add b-on-g/mol_skill --all -g
```

Дальше спрашивайте своими словами («устройство MAM-модуля», «CRUD и роли в Гипер Базе»), и ассистент откроет подходящий справочник до того, как ответит, так что код будет следовать соглашениям из этой документации. [Исходники](https://github.com/b-on-g/mol_skill) лежат на GitHub, а сами справочные файлы прекрасно читаются и по отдельности, если хочется пройтись по ним самому.
