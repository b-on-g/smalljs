# 모듈 메타데이터

모듈의 컴포넌트와 나란히, `name.meta.tree` 파일은 **빌드와 배포 메타데이터**를 선언합니다——개별 뷰가 아니라 모듈 전체에 관한 것들입니다. 앱 모듈이 그것을 두는 보통의 자리입니다.

다음은 이 사이트의 `app.meta.tree`입니다:

```tree
include \/mol/offline/install
include \/bog/builderui/theme.css
deploy \/bog/smalljs/assets
```

## 디렉티브

- **`deploy \/path`**——지정한 파일이나 폴더를 프로덕션 빌드 출력으로 복사합니다. 배포가 지녀야 하지만 어떤 코드도 임포트하지 않는 정적 자산——이미지, 폰트, 아이콘——에 사용하세요. 여기서 `\/bog/smalljs/assets`는 로고와 `assets/` 아래의 다른 파일들을 함께 실어 보냅니다.
- **`require \/path`**——어떤 코드도 참조하지 않더라도 모듈을 번들에 강제로 넣습니다. 그 모듈의 코드가 이 `meta.tree`를 가진 모듈의 코드보다 **먼저** 실행되어야 하는 경우를 위해서입니다. 일반적인 높은 우선순위 의존성으로 포함됩니다. 모듈 경로(`\/mol/wire/patch`)나 단일 파일 모두 됩니다.
- **`include \/path`**——같은 강제 포함이지만, 로드 순서가 중요하지 않은 경우를 위해서입니다. 모듈은 포함되지만 우선순위가 낮아져서, 그것에 의존하는 코드 뒤에 로드됩니다. 예: `include \/mol/offline/install`(부수 효과로 서비스 워커를 등록) 및 `include \/bog/builderui/theme.css`(원시 스타일시트).
- **`pack <name> git \<url>`**——네임스페이스를 MAM이 그것을 가져오는 git 저장소에 매핑합니다. 예: `pack mol git \https://github.com/hyoo-ru/mam_mol.git`. `$mol_*`, `$hyoo_*`, 그리고 여러분 자신의 패키지가 바로 이것으로 실제 코드로 해석됩니다.

대체 왜 포함을 강제할까요? 빌더는 의존성을 자동으로 알아내고, 여러분의 코드가 실제로 쓰는 것만 번들에 넣습니다. 가끔 여러분의 코드가 참조하지 *않는* 모듈이 필요합니다——예를 들어 컴포넌트 카탈로그 전체를 런타임에 존재시키려고 번들에 넣는 앱입니다. `require`와 `include`가 바로 그 경우를 다룹니다; 둘은 로드 순서에서만 다릅니다.

## 그것은 어디에 있나

`pack` 선언은 **워크스페이스 루트**의 `.meta.tree`에 속합니다——그것은 워크스페이스가 가져올 수 있는 모든 패키지의 레지스트리입니다. 서브모듈이 아니라 거기에 두세요; 서브모듈 자신의 `meta.tree`는 그것에 특유한 `require`/`include`/`deploy`만 지녀야 합니다.
